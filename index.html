02 컴퓨터와 프로그램

문법 전에 “프로그램이 뭘 하는 물건인지”만 잡으면 뒤 설명이 전부 연결됩니다.

한 줄 비유

컴퓨터는 받은 정보(입력)를 계산·판단(처리)해서 결과(출력)를 보여 주고, 필요하면 기억(저장)하는 기계입니다. 프로그램은 그 일을 시키는 설명서입니다.

부품역할게임으로 치면
CPU명령 계산이동·충돌·점수 계산
RAM지금 쓰는 작업 공간플레이어 좌표, 임시 상태
저장장치오래 보관설치 파일, 세이브
GPU화면 그리기 연산캐릭터·이펙트 렌더
C++와 연결: 변수·배열·객체는 대부분 RAM 이야기고, 코드는 CPU가 실행하는 명령입니다. → 10 · 스택과 힙으로 이어집니다.

03 컴파일과 실행

사람이 쓴 글이 컴퓨터가 읽을 말로 바뀌는 과정입니다.

소스 → 실행 파일

C++ 파일은 사람이 읽기 좋은 텍스트입니다. 컴파일러가 이를 기계어(실행 파일)로 바꿉니다.

1
소스 코드 .cpp — 우리가 편집하는 파일
2
컴파일 — 문법 검사 + 기계어 변환 (에러 나면 여기서 멈춤)
3
실행 — OS가 프로그램을 메모리에 올리고 CPU가 실행
팁: “실행이 안 돼요”의 절반은 컴파일 에러입니다. 빨간 줄·터미널 메시지를 번역기라도 읽으면 성장이 빨라집니다.

.h 와 .cpp — 약속서와 작업장

파일비유주로 넣는 것
.h / .hpp 메뉴판 · 약속서 선언 (이름, 시그니처, 클래스 골격)
.cpp 주방에서 만드는 과정 정의 (실제 코드 본문)

프로젝트가 커지면 분할 컴파일 — 바뀐 .cpp만 다시 컴파일하고, 마지막에 링크해서 실행 파일을 만듭니다.

#include

#include <iostream>  // 표준 라이브러리 쪽
#include "Player.h"    // 내 프로젝트 쪽
  • < > — 표준/시스템 경로
  • " " — 보통 현재 프로젝트 헤더
  • 전처리 단계에서 파일 내용을 붙인 뒤 컴파일

헤더 가드

// Player.h
#pragma once   // 한 번만 include (현대 습관)

// 또는 전통 방식
#ifndef PLAYER_H
#define PLAYER_H
// ... 선언 ...
#endif

같은 헤더가 여러 번 붙으면 중복 정의 에러 → 가드로 막습니다.

지금은 여기까지: “선언(.h) / 정의(.cpp) / include로 가져오기”. 링크·ABI·매크로 심화는 나중에. 설치 한 줄 명령도 OS별로 추후 보강.

04 첫 프로그램

모든 C++ 프로그램은 대략 main에서 시작합니다.

#include <iostream>   // 입출력 도구 상자

int main() {
    std::cout << "Hello!\n";  // 화면에 출력
    return 0;                 // 정상 종료
}
  • #include = 필요한 도구 가져오기 (03)
  • std::cout = 표준 출력(화면)
  • return 0 = “문제 없이 끝났어요”
  • std = 표준 네임스페이스 (아래)
  • 이 repo의 src/hello.cpp로 첫 컴파일 확인

std 네임스페이스

std = standard namespace. 표준 라이브러리 이름(cout, string, vector…)이 모인 구역. 

std::cout << "hi\n";     // 권장: 구역을 밝힘
// using namespace std;   // 초보 예제에선 편하지만, 이름 충돌 주의

입출력 — cin / cout

상황: 화면에 쓰고, 키보드로 값을 받는다.

#include <iostream>
#include <string>

int main() {
    std::string name;
    int score = 0;

    std::cout << "이름: ";   // 출력
    std::cin >> name;        // 입력 (공백 전까지만)
    std::cout << "점수: ";
    std::cin >> score;

    std::cout << name << " = " << score << "\n";
}
  • << 출력 방향 (객체 → 화면)
  • >> 입력 방향 (키보드 → 변수)
  • 공백 포함 한 줄은 나중에 getline (심화/필요 시)

쓰임: 콘솔 도구, 디버그 로그, 간단한 설정 입력.

05 변수와 타입

변수 = 이름 붙인 상자. 타입 = 상자에 넣을 종류의 라벨. 프로그램은 결국 “값을 담아 두고 → 읽고 → 바꾸는” 일의 반복입니다.

자주 쓰는 타입

타입무엇을 담나대략 크기*예시
bool참/거짓1 bytebool alive = true;
char문자 하나1 bytechar key = 'A';
int정수4 byteint hp = 100;
float실수(단정)4 bytefloat t = 0.016f;
double실수(배정)8 bytedouble dist = 3.14;
std::string문자열가변std::string name = "Kim";

*크기는 환경·컴파일러에 따라 달라질 수 있습니다. “대략 이 정도”로 기억하면 됩니다.

상황 · 코드 · 쓰임

상황: 플레이어 이름·레벨·생존 여부를 한 화면에서 다룬다.

#include <iostream>
#include <string>

int main() {
    std::string name = "Hero";
    int level = 1;
    bool alive = true;

    std::cout << name << " Lv." << level
              << (alive ? " (alive)\n" : " (down)\n");
}

쓰임: UI 상태, 세이브 데이터 필드, 컴포넌트 멤버 변수 — 전부 “타입 있는 상자”입니다.

선언과 대입

int score;      // 선언 (값은 미정일 수 있음)
score = 0;      // 대입
int combo = 3;  // 선언 + 초기화 (권장)
습관: 만들 때 바로 초기값 넣기. “쓰레기 값” 실수를 줄입니다.

signed / unsigned 한 줄

  • int — 음수·양수 (일반 선택)
  • unsigned — 0 이상만 (개수·인덱스 등)
  • 섞어 쓰면 비교·뺄셈이 헷갈릴 수 있음 → 처음엔 int로 통일

진법 — 2진 · 10진 · 16진

컴퓨터 안 값은 결국 0과 1(비트)입니다. 같은 수를 쓰기만 다르게 할 수 있고, C++ 코드·메모리 덤프·색상 코드에서 표기가 섞여 나옵니다.

같은 값 · 세 가지 쓰기

10진 (decimal) 120
=
16진 (hex) 0x78
=
2진 (binary) 0b01111000

비트 8개 = 1바이트 · 16진 2자리

0 1 1 1
7상위 4비트
1 0 0 0
8하위 4비트

16진 한 자리 = 비트 4개 (니블) · 그래서 0x78 ↔ 0111 1000

이름밑쓰는 숫자C++ 표기언제 보나
10진 100–9 120 일상 숫자, HP·점수
16진 160–9, A–F 0x78 메모리 덤프, 색 #FF8800, 마스크
2진 20, 1 0b01111000 비트 플래그, 하드웨어 비트

A=10 … F=15. 대소문자 모두 가능 (0xFF = 0xff). 0b 접두사는 C++14부터.

상황 · 코드 · 쓰임

상황: “같은 상수”를 읽기 쉬운 진법으로 적고 싶다.

int a = 120;          // 10진
int b = 0x78;         // 16진  (b == a)
int c = 0b01111000;   // 2진   (c == a)  // C++14+

// 출력 진법 바꾸기
std::cout << std::hex << a << "\n";  // 78
std::cout << std::dec << a << "\n";  // 120
// 2진 출력은 비트 루프나 C++20 format 등

쓰임: 색상·플래그·주소·파일 매직 넘버는 16진이 읽기 쉽고, 점수·카운트는 10진이 자연스럽습니다.

왜 16진을 많이 쓰나?

  • 4비트 = 16진 1자리 — 2진을 짧게 묶음
  • 1바이트 = 16진 2자리 — 0x00~0xFF (0~255)
  • 덤프 78 56 34 12 처럼 바이트 단위로 읽기 편함
  • 엔디안(25)에서 보는 0x12345678 도 “의미”를 16진으로 쓴 것
이어지기: 비트 연산 → 06 연산자 · 바이트 줄 서기 → 25 엔디안 · 안 바꿀 값 고정 → 30 const

06 연산자

값에 대해 계산·비교·논리를 수행하는 기호. 게임 로직의 “수식”이 여기 모입니다.

종류 한눈에

종류기호한 줄
산술+ - * / %더하기·빼기·곱·나누기·나머지
대입= += -= *= /=상자에 넣거나 누적
증감++ --1 늘리기 / 줄이기
비교== != < > <= >=참/거짓 만들기
논리&& || !그리고 / 또는 / 아님
비트& | ^ ~ << >>플래그·마스크 (맛보기)

상황 · 코드 · 쓰임

상황: 점수 가산, 쿨다운 감소, “살아 있고 탄약이 남았는지” 판정.

int score = 100;
score += 50;           // 150  (score = score + 50)
++score;               // 151

int ammo = 3;
bool canFire = (ammo > 0) && alive;

// 함정: 정수 나눗셈
int a = 5 / 2;         // 2  (소수 버림)
double b = 5.0 / 2.0;  // 2.5

쓰임: 데미지 공식, 이동 속도, 조건 플래그, 타이머 틱.

++ 앞/뒤 (감각)

int i = 0;
int a = ++i;  // i=1, a=1  (먼저 증가)
int b = i++;  // b=1, i=2  (나중에 증가)

루프에선 보통 ++i 습관. 차이는 “그 식의 값”.

비트 맛보기

// 플래그 on/off  (2진·16진 감각 → 05 진법)
unsigned flags = 0;
flags |= 1u << 0;   // 0번 비트 on  (= 0b0001)
bool on = flags & (1u << 0);

충돌 레이어·옵션 묶음에 자주. 0b/0x 읽기 → 05 진법.

다음 단계: 기본 타입 기호는 여기(06). Point 같은 내 타입에 + 를 붙이려면 → 13 · 연산자 오버로딩 (클래스 이후).

07 조건과 반복

if는 갈림길, for / while은 같은 일을 여러 번. “언제 갈라지고, 몇 번 도는가”가 프로그램의 흐름입니다.

if / else — 갈림길

상황: HP에 따라 메시지·상태를 바꾼다.

int hp = 30;
if (hp <= 0) {
    std::cout << "Game Over\n";
} else if (hp < 30) {
    std::cout << "Danger\n";
} else {
    std::cout << "OK\n";
}

쓰임: 사망 판정, 등급 컷, 버튼 활성/비활성, 충돌 후 반응.

for — 횟수가 정해진 반복

상황: 3틱 카운트, N명의 적 순회 전 단계.

for (int i = 0; i < 3; ++i) {
    std::cout << "tick " << i << "\n";
}
// i = 0, 1, 2  → 세 번

쓰임: 배열/목록 순회, 웨이브 카운트, UI 슬롯 그리기 루프.

while — 조건이 참인 동안

상황: 체력이 남아 있는 동안 턴을 돌린다.

int hp = 100;
while (hp > 0) {
    hp -= 40;
    std::cout << "HP " << hp << "\n";
}
주의: 조건을 깨는 변화(hp -= …)가 없으면 무한 루프. 엔진 틱에서는 보통 “매 프레임 한 번” 구조라 while보다 for/이벤트 분기가 더 흔합니다.

switch — 여러 갈래 중 하나

상황: 상태가 0/1/2처럼 이산 값일 때 if 나열 대신 고른다.

int state = 1; // 0=Idle, 1=Run, 2=Jump
switch (state) {
    case 0: std::cout << "Idle\n"; break;
    case 1: std::cout << "Run\n";  break;
    case 2: std::cout << "Jump\n"; break;
    default: std::cout << "?\n";   break;
}
  • break — 그 case만 실행하고 빠져나옴
  • break 빠짐 → 아래 case로 흘러내림(fall-through)
  • default — 나머지 모든 경우

쓰임: 상태 머신, 메뉴 번호, 키 코드 분기. 복잡한 범위 비교는 if가 더 낫다.

enum — 이름 붙인 정수 집합

enum(enumeration, 열거형) = 의미 있는 이름에 숫자를 붙인 타입. “매직 넘버 0,1,2” 대신 읽기 좋게. 

enum class State { Idle, Run, Jump };  // 권장: enum class

State s = State::Run;
switch (s) {
    case State::Idle: /* ... */ break;
    case State::Run:  /* ... */ break;
    case State::Jump: /* ... */ break;
}
  • enum class — 이름이 구역 안 (State::Run) · 타입 안전
  • 옛 enum Direction { Left, Right }; 는 전역에 이름이 풀림
  • switch와 단짝

쓰임: 캐릭터 상태, 아이템 종류, AI 모드, UI 탭 인덱스.

08 함수

일을 묶은 레시피 카드. 이름 한 번으로 같은 처리를 여러 곳에서 호출합니다.

기본 형태

// 반환타입 이름(매개변수...) { 본문 }
int add(int a, int b) {
    return a + b;
}

void shout(const std::string& msg) {
    std::cout << msg << "\n";
    // return 없음 (void)
}
  • 입력(매개변수) → 처리 → 출력(return)
  • void = 돌려줄 값 없음 (출력·상태 변경만)
  • 함수 안 지역 변수는 끝나면 사라짐 → 10 · 스택 · 깊게는 26 프레임

상황 · 코드 · 쓰임

상황: 데미지 계산을 스킬·함정·충돌에서 같이 쓰고 싶다.

int applyDamage(int hp, int dmg) {

재귀 맛보기 — 자기 자신을 부르기

재귀(recursion) = 함수가 자기 자신을 다시 호출하는 것. “더 작은 같은 문제”로 쪼개 풀 때 읽기 쉬운 경우가 있습니다.

상황: n부터 1까지 곱한 값(팩토리얼)을 구한다. 0! = 1.

// n! = n * (n-1) * … * 1
int fact(int n) {
    if (n <= 1) return 1;   // 1) 종료 조건 (베이스 케이스)
    return n * fact(n - 1); // 2) 더 작은 문제로 자기 호출
}

// fact(4)
// → 4 * fact(3)
// → 4 * (3 * fact(2))
// → 4 * (3 * (2 * fact(1)))
// → 4 * (3 * (2 * 1)) = 24
  • 종료 조건 — 없으면 영원히 호출 → 위험
  • 한 걸음 작게 — 인자/상태가 종료 쪽으로 움직여야 함
  • 같은 일을 for/while로도 쓸 수 있는 경우가 많음
  • 깊이·입력이 커지면 스택이 쌓여 터질 수 있음
// 같은 뜻의 반복 (비교)
int factLoop(int n) {
    int r = 1;
    for (int i = 2; i <= n; ++i)
        r *= i;
    return r;
}

쓰임: 트리·폴더 순회, 분할 정복 알고리즘, 문법이 “자기 참조”인 구조. 게임 루프·단순 합산은 보통 반복이 더 단순합니다.

깊게: 호출할 때마다 스택 프레임이 쌓입니다 → 26 스택 프레임 · 재귀·오버플로

10 스택과 힙

둘 다 RAM 안의 작업 공간입니다. 차이는 문법 이름보다 누가 관리하고, 얼마나 오래 사느냐에 가깝습니다.

한눈에 비교

스택 (Stack)힙 (Heap)
관리자동 (함수 끝나면 정리)프로그래머 / 스마트 포인터
속도매우 빠름상대적으로 느림

비유계산용 메모지 (끝나면 버림)창고 대여 (반납 규칙 필요)
수명블록/함수와 함께직접 끊을 때까지 (또는 스마트 포인터)

메모리 도식 (개념 + 애니메이션)

물리적으로는 더 복잡하지만, 학습용으로 RAM을 구역으로 나눠 보면 됩니다. 스택은 위에서 아래로, 힙은 아래에서 위로 차곡차곡 늘어납니다.

함수 호출 → 스택 블록 · 동적 할당 → 힙 블록

스택 (자동) 빈 공간 힙 (동적) 전역/정적 코드
기억: 스택은 “함수 끝나면 자동 청소”, 힙은 “빌려 쓴 뒤 반납 규칙이 필요”. 반납을 현대적으로 다루는 법은 16 · 스마트 포인터. 세그먼트·가상 메모리·캐시·스택 프레임 → 심화 22+ · 26 프레임.

상황 · 코드 · 쓰임 — 스택

상황: 함수 안에서만 쓰는 임시 계산, 작은 상태.

void tick() {
    int damage = 10;     // 스택 (지역)
    int shield = 3;      // 스택
    int net = damage - shield;
    // tick이 끝나면 damage, shield, net 전부 사라짐
}

쓰임: 매 프레임 임시 값, 루프 카운터, 작은 구조체 값 — 기본은 스택이 안전하고 빠름.

상황 · 코드 · 쓰임 — 힙이 필요한 때

상황: “함수가 끝나도” 살아 있어야 하거나, 크기를 실행 중에 정해야 할 때.

// 개념만 (raw new는 나중에 스마트 포인터로 대체)
int* big = new int[1000];  // 힙에 1000칸
// ... 여러 함수에서 big을 넘기며 사용 ...
delete[] big;              // 반납 (안 하면 누수)

쓰임: 긴 수명의 리소스, 큰 버퍼, 프로그램이 끝날 때까지 살아 있어야 하는 데이터. 일상 목록은 보통 vector(14)가 힙을 대신 관리해 줍니다.

지금 목표: raw new 숙달이 아니라 “스택 = 자동 / 힙 = 수명 설계” 감각. 상세 할당은 14, 안전한 소유는 15.

선택 가이드

  • 작다 + 함수 안에서만 → 스택 (일반 변수)
  • 목록이 늘어난다 → vector (14)
  • 소유·수명이 복잡 → 스마트 포인터 (16)
  • 초보 구간에서 raw new 남발

11 포인터와 참조

값 vs 그 값이 있는 곳(주소). 목표는 100% 숙달이 아니라, 머리속에 화살표 그림이 그려지는 것입니다.

한 줄 정의

  • 포인터 — 주소를 담는 변수. 화살표를 들고 다님.
  • 참조 — 이미 있는 변수에 붙인 별명. 문법상 값처럼 씀.
  • 둘 다 “복사본이 아니라 원본을 건드리고 싶을 때” 등장

한눈에 보기 — 화살표 애니메이션

p는 주소를 들고 x를 가리키고, *p로 따라가 값을 바꿉니다. 아래쪽 r은 같은 상자의 별명(참조)입니다.

1) x → 2) p 화살표 → 3) *p로 값 변경 → 4) r 별명

포인터 p (주소) 변수 x (값) 참조 r (별명)

포인터 — 주소와 역참조

상황: 변수 x가 있는 위치를 다른 이름으로 찾아가 수정.

int x = 10;
int* p = &x;   // &x = x의 주소, p가 그 화살표를 보관
*p = 20;       // * = 따라가서 값 쓰기 → x도 20
기호읽는 법
int* pp는 “int가 있는 곳”을 가리킴
&xx의 주소 (화살표 만들기)
*pp가 가리키는 그 값 (따라가기)
nullptr아무 데도 안 가리킴 (빈 화살표)

쓰임: 배열 Decay, C API, “있을 수도 없는 대상” 핸들, 선택적 객체.

참조 — 별명

상황: 함수에 넘길 때 복사 없이 원본 HP를 바꾸고 싶다.

void hurt(int& hp, int dmg) {
    hp -= dmg;          // 원본이 바뀜
    if (hp < 0) hp = 0;
}

int main() {
    int playerHp = 100;
    hurt(playerHp, 30); // playerHp == 70
}

참조는 선언 시 반드시 누군가를 가리켜야 하고, 보통 다시 “다른 대상”으로 갈아끼우지 않습니다.

쓰임: 함수 인자(T&, const T&), 큰 객체 읽기, 범위 for (for (auto& e : list)).

포인터 vs 참조 (실무 감각)

const 참조 (읽기 전용 별명)

큰 객체를 복사 없이 읽기만 할 때 자주 씁니다.

void printName(const std::string& s) {
    std::cout << s;  // 수정 안 함
    // s[0] = 'A';  // 불가 (const)
}

쓰임: 함수 인자로 string/구조체 전달, 읽기 전용 참조 인자.

위험 신호 (이름만)

  • 댕글링 — 이미 사라진 대상을 가리킴
  • 널 역참조 — nullptr에 *
  • 소유·해제는 스마트 포인터로 (16)
  • 참조는 보통 “항상 유효한 별명”으로 씀

12 구조체와 클래스

흩어진 변수·함수를 한 타입(설계도)으로 묶습니다. 게임의 캐릭터·아이템·스킬이 거의 이 패턴입니다.

한 줄로

  • 멤버 변수 = 상태 (이름, HP, 좌표…)
  • 멤버 함수 = 행동 (데미지 받기, 이동…)
  • struct / class — 거의 같고, 기본 접근 권한만 다름

한눈에 보기 — 객체 상자

설계도(Player)로 만든 실제 덩어리가 객체입니다. 상태와 행동이 한 박스 안에 있습니다.

상태(멤버) → 행동(멤버 함수) 순으로 등장

OOP 한 줄

OOP(Object-Oriented Programming, 객체지향) = 프로그램을 “기능 나열”이 아니라 역할·상태를 가진 객체들의 협력으로 보는 방식.

  • 객체 = 상태 + 행동 (위 박스)
  • 상속·다형성은 나중에 얇게

public / private — 문을 열까 닫을까

public = 밖에서도 씀 · private = 타입 안에서만. “함부로 만지면 깨지는 상태”는 감추고, 행동(함수)으로만 다루게 합니다. 

class Player {
public:
    Player(std::string n, int h) : name(n), hp(h) {}

    void takeDamage(int dmg) {   // 밖에서도 호출 OK
        hp -= dmg;
        if (hp < 0) hp = 0;
    }
    int getHp() const { return hp; }

private:
    std::string name;            // 밖에서는 직접 수정 불가
    int hp;
};

// p.hp = 999;  // 컴파일 에러 (private)
// p.takeDamage(10);  // OK

쓰임: 라이브러리 API — “써도 되는 면”과 “내부 구현”을 나눔.

생성자 · 멤버 초기화 리스트

생성자(constructor) = 객체가 생길 때 자동 실행되는 특수 함수. 이름 = 타입 이름, 반환 타입 없음. 

class Player {
public:
    // 멤버 초기화 리스트 (: 뒤) — 본문보다 먼저, 권장
    Player(std::string n, int h)
        : name(std::move(n)), hp(h) {
        // 필요하면 추가 작업
    }

private:
    std::string name;
    int hp;
};

Player a("Hero", 100);     // 생성자 호출
Player b{ "Mage", 80 };    // 동일 취지 (균일 초기화)

  • 본문 안 hp = h; 보다 초기화 리스트가 기본 습관
  • 인자 없는 생성자·여러 개 생성자(오버로드) 가능

소멸자

소멸자(destructor) = 객체가 사라질 때 자동 실행. 이름 ~타입.

class Session {
public:
    Session() { /* 열기 */ }
    ~Session() { /* 닫기·정리 */ }
};
// 스코프 끝 → ~Session() 호출

raw 자원이 없으면 기본 소멸자로 충분한 경우가 많음. 소유 정리는 보통 16 · 스마트 포인터 / RAII와 함께.

this 포인터

멤버 함수 안에서 나 자신(이 객체)을 가리키는 포인터.

void Player::setHp(int hp) {
    this->hp = hp;  // 멤버 hp = 인자 hp
}
// 이름이 안 겹치면 this-> 생략 가능

“인자 이름과 멤버 이름이 같을 때” 자주 보임. 포인터 감각은 11.

한 장에 모은 예

class Player {
public:
    Player(std::string n, int h) : name(std::move(n)), hp(h) {}
    ~Player() = default;   // 특별한 정리 없으면 기본

    void takeDamage(int dmg) {
        hp -= dmg;
        if (hp < 0) hp = 0;
    }
    int getHp() const { return hp; }  // const: 상태 안 바꿈

private:
    std::string name;
    int hp;
};

읽기 순서: private 상태 → public 생성/행동 → 밖에서는 함수로만 건드림.

지금은 여기까지: 묶기 · 열고 닫기(public/private) · 생김/사라짐(생성/소멸) · this. 멤버 패딩 → 27 · 상속·가상 → 28 · 소멸/복사/이동 규칙 → 29. 타입에 +·== → 13.

13 연산자 오버로딩

연산자 오버로딩(operator overloading) = +, == 같은 기호를 내 타입에도 쓰이게 만드는 것. 기호가 사실은 함수 호출이 됩니다.

한 줄로

  • a + b → 컴파일러가 a.operator+(b) (또는 전역) 로 해석
  • 벡터·행렬·점수 타입에 “자연스러운 수식”을 줄 때
  • 모든 기호를 다 오버로드할 필요 없음 · 의도가 흐려지면 독이 됨

한눈에 보기 — 기호가 함수가 되다

p1 + p2 가 operator+ 호출로 바뀌는 그림입니다.

수식 → operator+ 호출 → 새 Point

피연산자 결과 객체

상황 · 코드 · 쓰임

상황: 2D 좌표 두 개를 더해 새 좌표를 만들고 싶다.

struct Point {
    float x = 0, y = 0;

    Point operator+(const Point& o) const {
        return Point{ x + o.x, y + o.y };
    }
};

Point a{1, 2}, b{3, 4};
Point c = a + b;   // (4, 6)

쓰임: 벡터·행렬 수학, 점수/머니 타입, “수식처럼 보이는” 사용자 정의 타입 API.

자주 오버로드하는 것

  • + - * (벡터/행렬)
  • == != (비교)
  • << 출력 (고급·취향) — 입문 필수 아님

지금은 여기까지

  • “기호 = 함수” 그림만 잡기
  • 모든 연산자 마스터 / 남용
  • 기본 연산자 기호는 06, 타입 묶음은 12

14 STL · vector

STL(Standard Template Library, 표준 템플릿 라이브러리) = 표준이 주는 자료구조·알고리즘 도구 상자. 그중 목록의 기본 선택은 std::vector 입니다.

왜 vector인가

  • 길이가 실행 중에 늘어남 (push_back)
  • 인덱스로 빠른 접근 (v[i])
  • 내부는 연속 메모리(배열 느낌) — 캐시에 유리한 편
  • C 배열(09)보다 실무 목록에 훨씬 자주 씀

한눈에 보기 — 늘어나는 칸

size = 지금 쓰는 개수, capacity = 미리 잡아 둔 칸. 칸이 모자라면 더 큰 공간을 잡아 옮깁니다(성장).

채움 → push_back → capacity 확장 여유

사용 중 (size) 여유 (capacity) 방금 push

상황 · 코드 · 쓰임

상황: 점수 목록을 만들고, 스폰처럼 뒤에 하나씩 추가.

#include <vector>
#include <iostream>

int main() {

    for (int s : scores) {          // 범위 for
        std::cout << s << "\n";
    }
    // scores.size() == 4
}

쓰임: 적 목록, 인벤토리, 웨이브 스폰 큐, 총알 풀(간단 버전).

15 new 와 delete

힙에 자리를 빌리고(new) 다 쓰면 반납(delete)하는 옛 방식. 감각만 잡고, 실무 기본은 15로 넘어갑니다.

한 줄로

  • new T → 힙에 T 하나, 주소를 돌려줌
  • delete p → 그 자리 반납
  • 반납 안 함 → 누수 / 반납 후 또 씀 → 댕글링

한눈에 보기 — 빌리고 반납

포인터 p는 스택에, 실제 값은 힙에. delete 뒤에도 주소 숫자가 남을 수 있어 위험합니다.

new → 연결 → delete 후 약해진 힙 · 댕글링 주의

포인터 (스택) 실제 값 (힙) new 연결

상황 · 코드 · 쓰임

상황: 실행 중에 크기를 정한 한 칸을 힙에 두고 싶다. (개념 학습용)

int* p = new int(42);   // 힙에 int, p가 주소 보관
std::cout << *p << "\n";
delete p;               // 반납
p = nullptr;            // 잘못된 재사용 방지 습관

쓰임: 레거시 API, 저수준 라이브러리, “직접 수명 관리”를 이해하는 데. 목록이면 vector(14), 소유 객체면 16 · 스마트 포인터가 기본.

배열 형태

int* a = new int[100];
// ...
delete[] a;   // 배열은 delete[]

new/delete 짝을 맞출 것.

현대 습관

  • 초보 코드에 raw new 남발
  • 목록 → vector
  • 단일 소유 객체 → unique_ptr
  • 여기는 “왜 위험한지” 감각용

malloc/free 와 new/delete — 무엇이 다른가

malloc/free는 C에서 물려받은 저수준 방식, new/delete는 C++가 얹은 방식. 핵심 차이는 “생성자·소멸자를 부르느냐”입니다.

항목malloc / freenew / delete
정체함수 (<cstdlib>)연산자 (언어 내장)
생성자·소멸자안 부름 (그냥 바이트만)부름 (객체를 제대로 초기화·정리)
크기 지정직접 sizeof 계산·바이트로타입으로 자동 (new T)
반환 타입void* (캐스팅 필요)T* (그대로 사용)
실패 시nullptr 반환std::bad_alloc 예외
짝freedelete · 배열은 delete[]
 
// malloc: 바이트만 확보 → 생성자 호출 안 됨
Player* a = (Player*)malloc(sizeof(Player));  // ✗ 멤버 초기화 안 됨
free(a);                                       // ✗ 소멸자도 안 불림

// new: 객체를 제대로 만들고(생성자) 지움(소멸자)
Player* b = new Player();   // ✓ 생성자 호출
delete b;                   // ✓ 소멸자 호출
섞지 말 것: new로 만든 건 delete, malloc한 건 free. 짝을 교차하면 미정의 동작. 그리고 실무에선 둘 다 직접 쓰기보다 16 · 스마트 포인터·vector(14)가 먼저입니다.

16 스마트 포인터

포인터처럼 쓰되, 수명이 끝나면 자동으로 반납하는 객체입니다. 핵심 습관이 RAII(Resource Acquisition Is Initialization: 자원을 객체 생성·소멸에 묶기) 입니다.

세 종류 (역할만)

타입한 줄언제
unique_ptr 소유자 하나 기본 선택 (거의 여기)
shared_ptr 여러 곳이 공유 소유 정말 공유할 때만 (남용 주의)
weak_ptr 소유 없이 관찰 shared 순환 끊기

한눈에 보기 — 스코프 끝 자동 해제

unique_ptr가 스코프를 벗어나면 가리키던 힙 객체도 함께 정리됩니다. delete를 손으로 안 씀.

unique_ptr 생성 → 소유 → 스코프 종료 시 자동 delete

unique_ptr (스택 객체) 소유 대상 (힙)

상황 · 코드 · 쓰임

상황: 세션·리소스 하나를 이 함수/이 객체가 단독 소유.

#include <memory>

void run() {
    auto session = std::make_unique<int>(42);
    // *session 또는 session.get() 로 접근
} // 여기서 자동 해제

쓰임: “이 모듈의 주인 하나”, 팩토리가 넘긴 뒤 소유권 이전(std::move → 17).

raw new 와의 차이

  • 예외가 나도 스택 풀리며 소멸 → 반납 기회
  • 소유자가 코드에 드러남
  • shared_ptr 남용 → 수명 추적 어려움

지금은 여기까지

  • 기본: unique_ptr + make_unique
  • shared/weak·순환 → 29
  • 규칙 오브 파이브 → 29

17 이동(move)

큰 데이터를 통째로 복사하는 대신, “이 자원의 주인”만 넘기는 것이 이동(move) 입니다. vector 성장·unique_ptr 전달과 잘 붙습니다.

한 줄로

  • 복사 — 내용 복제 (시간·메모리 비용)
  • 이동 — 소유권 이전 (핸들/포인터만 넘기는 그림)
  • std::move = “이제 이건 옮길 수 있는 값으로 취급해” 표시

한눈에 보기 — 복사 vs 이동

위: 복사하면 데이터가 두 벌. 아래: 이동하면 자원이 B로 넘어가고 A는 비어 있는 상태에 가깝습니다.

복사(복제) → 이동(소유권 이전)

복사 = 복제 이동 = 소유권

상황 · 코드 · 쓰임

상황: unique_ptr 소유권을 다른 변수/함수로 넘긴다.

#include <memory>
#include <utility>  // std::move

auto a = std::make_unique<int>(42);
auto b = std::move(a);  // 소유권이 b로
// a 는 비어 있음(nullptr에 가깝게 취급)
// *b == 42

쓰임: 팩토리가 객체를 호출자에게 넘김, 컨테이너에 큰 객체 넣기, 반환값 최적화와 맞물린 성능.

지금은 여기까지: “비싸면 복사 대신 이동을 생각”. 이동 생성자 직접 구현·규칙 오브 파이브 전체 → 29.

18 템플릿

타입을 매개변수처럼 넘기는 문법입니다. 같은 로직을 int/double에 복붙하지 않게 해 주고, STL의 기반이기도 합니다.

한 줄로

  • 함수/클래스 옆에 template <typename T>
  • 컴파일할 때 실제 타입으로 “찍어 냄” (런타임 마법이 아님)
  • vector<int>, unique_ptr<T> 가 전부 이 계열

한눈에 보기 — 한 틀, 여러 타입

하나의 템플릿 정의가 int용·double용 코드로 각각 생성되는 그림입니다.

템플릿 정의 → int / double 인스턴스

템플릿 틀 int 인스턴스 double 인스턴스

상황 · 코드 · 쓰임

상황: 더 큰 값을 고르는 로직을 여러 타입에 쓰고 싶다.

template <typename T>
T max2(T a, T b) {
    return (a > b) ? a : b;
}

// 사용
max2(1, 2);       // T = int
max2(1.5, 0.2);   // T = double

쓰임: 컨테이너(vector<T>), 스마트 포인터, 유틸 함수 한 벌로 여러 타입 지원.

함수 vs 클래스 템플릿 (맛보기)

  • 함수 템플릿 — 위 max2
  • 클래스 템플릿 — vector<T>, unique_ptr<T>
  • 에러 메시지가 길어질 수 있음 (컴파일러가 타입을 펼침)

지금은 여기까지

  • “타입을 인자처럼” 읽기
  • 템플릿 메타프로그래밍 심연

22 세그먼트 BSS · DATA · TEXT

심화

메인 10 · 스택과 힙의 확장. 실행 파일이 RAM에 올라가면 구역이 더 잘게 나뉩니다. 이름만 알아도 “전역이 어디에 사나”가 잡힙니다.

관련 메인 10 스택과 힙 03 컴파일 15 new

1. 프로세스 주소 공간 — 그림

흔한 학습용 배치(위에서 높은 주소). OS·아키텍처마다 세부는 다르지만 역할 구분은 같습니다.

높은 주소↑
STACK 지역 변수 · 함수 호출 프레임 아래로 자람 ↘
··· 빈 공간 (서로 마주 보며 자람) ···
HEAP new · vector 버퍼 등 동적 위로 자람 ↗
BSS 초기값 없는 전역·정적 실행 시 0 채움
DATA 초기값 있는 전역·정적 파일에 값이 실림
TEXT 기계어 코드 (읽기·실행) 명령이 있는 곳
낮은 주소↓

TEXT·DATA·BSS는 실행 파일/로더 쪽 · HEAP·STACK은 실행 중 커짐

2. 한눈에 표

구역무엇이 있나한 줄
TEXT기계어 코드실행할 명령 · 보통 쓰기 금지
DATA초기값 있는 전역/정적실행 파일에 바이트가 실림
BSS초기값 없는 전역/정적크기만 기록, 실행 시 0
HEAP동적 할당new / 컨테이너 버퍼 → 15
STACK지역·호출함수와 함께 생멸 → 10

3. 왜 BSS가 있나

초기값 없는 큰 전역 배열을 DATA에 넣으면 실행 파일에 0 이 잔뜩 들어가 파일이 커집니다. BSS는 “몇 바이트 필요하다”만 적고, 실행 때 OS가 0으로 채웁니다. 

int buf[1'000'000]; // 초기값 없음 → 대개 BSS
int ready = 1;        // 초기값 있음 → DATA
static int cnt;       // 정적·미초기화 → BSS 쪽

4. 상황 · 코드 · 쓰임

상황: 전역 설정 플래그와 큰 버퍼를 나눈다.

// 파일 스코프 (전역)

                      // DATA/BSS 경계는 구현마다 다를 수 있음)
char g_log[4096];     // 미초기화 배열 → 대개 BSS

int main() {
    int local = 1;    // STACK
    auto* p = new int[64]; // HEAP
    delete[] p;
}

  • 권한 분리 (코드 페이지 쓰기 금지 등)

25 엔디안 (리틀 / 빅)

심화

int 같은 값은 보통 여러 바이트입니다. 그 바이트들을 메모리에 어떤 순서로 줄 세울지가 엔디안(endianness) 입니다. 같은 숫자라도 메모리·파일·네트워크에 찍히는 “바이트 줄”이 달라질 수 있습니다.

관련 메인 05 변수·진법 06 연산자 10 스택과 힙 11 포인터

1. 문제를 먼저 잡기

사람이 쓰는 수 0x12345678 은 “의미”입니다 (16진 표기 — 05 진법). 메모리 주소는 한 칸에 1바이트씩 번호를 매깁니다. 4바이트 정수를 쓰려면 주소 4칸이 필요하고, 그때 어느 칸에 어느 바이트를 넣을지 규칙이 필요합니다.

용어뜻
MSB Most Significant Byte — 큰 자리 바이트 (예: 0x12)
LSB Least Significant Byte — 작은 자리 바이트 (예: 0x78)
낮은 주소 포인터가 가리키는 시작 쪽 (&x, addr+0)
  • 리틀 엔디안 — 낮은 주소에 LSB (x86 / x64 Windows·대부분의 PC)
  • 빅 엔디안 — 낮은 주소에 MSB (전통 네트워크 바이트 오더, 일부 CPU)

2. 같은 값, 다른 메모리 줄 — 그림

값 uint32_t v = 0x12345678; (MSB=12 … LSB=78)

사람이 hex로 읽을 때 익숙한 순서(12 34 56 78)는 빅 쪽과 비슷하고, 지금 PC(Windows x64) 메모리를 바이트로 까보면 보통 리틀(78 56 34 12)이 나옵니다.

3. 왜 이렇게 설계됐을까?

역사적으로 CPU·칩 설계마다 “편리한 쪽”이 달랐고, 표준이 하나로 굳지 않았습니다.

리틀이 편한 점 (하드웨어 관점)

  • 여러 바이트 덧셈은 낮은 자리(LSB)부터 올림을 처리 → 낮은 주소부터 읽으면 자연스러움
  • 같은 시작 주소에서 1바이트만 읽으면 “가장 작은 자리”를 바로 얻음
  • Intel x86 계열이 리틀을 널리 퍼뜨림 → 오늘날 PC·노트북 대부분

빅이 편한 점 (사람·통신 관점)

  • 메모리 덤프를 왼쪽→오른쪽으로 보면 사람이 쓰는 hex 순서와 비슷
  • 인터넷 초창기 프로토콜이 “네트워크 바이트 오더 = 빅”으로 관례화
  • 그래서 소켓 API에 htonl / ntohl 같은 변환이 있음
핵심: “어느 쪽이 절대적으로 우월”해서가 아니라, 같은 규칙으로 쓰고 읽기만 하면 됩니다. 문제가 되는 경우는 규칙이 다른 세계가 만날 때 (파일·다른 CPU·네트워크).

4. 예시 코드 — 내 PC에서 바이트 까보기

값을 “숫자”로 보지 말고, 그 주소의 바이트 배열로 해석해 봅니다. (대부분의 Windows PC = 리틀 엔디안) 

#include <cstdint>
#include <cstdio>
#include <cstring>

int main() {
    std::uint32_t v = 0x12345678u;

    // 방법 1: 주소를 unsigned char* 로 해석 (바이트 단위)
    auto* p = reinterpret_cast<unsigned char*>(&v);

    std::printf("value = 0x%08X\n", v);
    std::printf("&v    = %p\n", static_cast<void*>(&v));
    for (int i = 0; i < 4; ++i) {
        std::printf("  addr+%d : 0x%02X\n", i, p[i]);
    }

    // 방법 2: memcpy 로 안전하게 복사
    unsigned char bytes[4];
    std::memcpy(bytes, &v, sizeof v);
    std::printf("memcpy bytes: %02X %02X %02X %02X\n",
                bytes[0], bytes[1], bytes[2], bytes[3]);
}

리틀 엔디안 PC에서 전형적인 출력:

// 실행 결과 예시 (Windows x64 · 리틀 엔디안) value = 0x12345678 &v = 0000005A3E0FFA14 // 주소는 매번 다름 addr+0 : 0x78 // LSB · 낮은 주소 addr+1 : 0x56 addr+2 : 0x34 addr+3 : 0x12 // MSB · 높은 주소 memcpy bytes: 78 56 34 12

디버거(Visual Studio 등)의 Memory 창에서 &v 를 보면 같은 줄이 보입니다. Watch에 v 만 보면 0x12345678 으로 “의미 있는 숫자”로 보여 주므로, 바이트 순서 착시가 안 납니다.

5. 디버그/메모리 뷰로 보면

// Watch 창 (논리적 값) v = 305419896 // 10진 v = 0x12345678 // 16진 · 의미 // Memory 창 (주소 오름차순, 리틀 엔디안 PC) 0x...FA14 78 56 34 12 .. .. .. .. ^-- &v 시작 // 만약 빅 엔디안 머신 메모리라면 (같은 v) 0x...FA14 12 34 56 78 .. .. .. ..

디버거가 Watch에서 값을 예쁘게 보여주는 것과, 메모리를 바이트 단위로 까보는 것은 다른 층입니다. 엔디안은 후자의 규칙입니다.

6. 실제로 사고가 나는 순간

상황: 리틀 엔디안 PC에서 파일에 4바이트를 “그대로” 쓰고, 빅 엔디안(또는 “네트워크 오더로 쓴” 파일)으로 해석하면 숫자가 달라집니다.

// 위험 패턴 감각 (의사 코드)
uint32_t v = 0x12345678;
write(file, &v, 4);          // 호스트 엔디안 그대로 덤프

// 다른 쪽이 "빅 엔디안 정수"로 읽으면
// 바이트 12 34 56 78 을 기대한 자리에
// 78 56 34 12 가 들어가 있음 → 값이 0x78563412 처럼 보임
상황엔디안을 안 맞추면
바이너리 세이브/로드HP·좌표가 엉뚱한 큰 수
소켓으로 int 전송수신 측 숫자가 뒤바뀜
같은 프로세스 안 변수 연산보통 문제 없음 (CPU가 규칙을 앎)
문자 배열·UTF-8 텍스트바이트 단위 약속이라 엔디안과 별개

7. 실무에서 쓰는 대응 감각

  • 같은 머신·같은 컴파일러 안 — 변수 연산만 하면 신경 거의 안 씀
  • 파일/네트워크 포맷 — “이 필드는 리틀/빅 고정”을 스펙에 적고, 읽고 쓸 때 변환
  • 네트워크: 전통적으로 빅 엔디안 = network byte order
  • C API 예: htonl / ntohl (host ↔ network long)
  • C++20 근처: std::endian 으로 컴파일 타임 확인 가능
#include <bit>   // C++20
// std::endian::native == std::endian::little  인지 확인 가능

// 수동으로 바이트 스왑 감각 (교육용)
std::uint32_t bswap32(std::uint32_t x) {
    return (x >> 24) | ((x >> 8) & 0x0000FF00u)
         | ((x << 8) & 0x00FF0000u) | (x << 24);
}

26 스택 프레임 · 호출 규약

심화

함수를 호출할 때마다 스택에 한 칸의 작업 공간이 쌓입니다. 그걸 스택 프레임(stack frame)이라 부릅니다. 메인 10 스택·08 함수의 “왜 지역 변수가 끝나면 사라지나”를 한 단계 깊게 봅니다.

관련 메인 08 함수 10 스택과 힙 11 포인터 22 세그먼트

1. 호출이 쌓이면 — 그림

예: main → attack → roll. 스택은 보통 높은 주소 → 낮은 주소로 자라고, 지금 실행 중인 함수 프레임이 맨 아래(최신)에 있습니다.

2. 프레임 안에 뭐가 들어가나 (감각)

요소한 줄
복귀 주소이 함수가 끝나면 어디로 돌아갈지 (호출한 쪽의 다음 명령)
인자넘겨받은 값. 레지스터에만 있을 수도, 스택에도 있을 수도 있음

저장 레지스터 등호출 규약에 따라 백업해 두는 자리 (세부 ABI)

“스택에 전부 있다”가 아니라, 논리적으로 한 호출의 작업 공간이 프레임입니다. 최적화되면 일부는 레지스터에만 살고 스택 슬롯이 없을 수도 있습니다.

4. 상황 · 코드 · 쓰임

상황: 데미지 계산이 함수 두 겹으로 나뉜다.

int roll(int n) {
    int r = n;          // roll 프레임 지역
    return r;
}
int attack(int base) {
    int bonus = 2;      // attack 프레임
    return base + roll(6) + bonus;
}
int main() {
    int hp = 100;       // main 프레임
    hp -= attack(15);
}

쓰임: 브레이크포인트 걸면 Call Stack에 roll ← attack ← main 이 보입니다.

5. 호출 규약 (맛보기)

  • calling convention — 인자·반환값을 어디서 주고받는지 약속
  • 현대 x64는 인자를 레지스터에 많이 넣음 (스택만은 아님)
  • Windows x64 / System V(Linux·mac) 규약이 다름 → 라이브러리 경계에서 중요
  • 초보가 손으로 ABI 표를 외울 필요는 없음

C++ 이름 맹글링·예외 테이블은 더 깊은 주제. 지금은 “호출마다 프레임 + 약속된 전달 방식”만.

6. 재귀 · 스택 오버플로

재귀(08 맛보기)는 같은 함수 프레임이 여러 겹 쌓입니다. 깊이가 너무 크면 스택 공간이 바닥나서 스택 오버플로(stack overflow)가 납니다. 

int sum(int n) {
    if (n <= 0) return 0;
    return n + sum(n - 1);  // 호출마다 프레임 +1
}
// sum(1000000) → 프레임이 백만 겹… 위험할 수 있음
  • 종료 조건이 없으면 프레임이 끝없이 쌓임
  • 큰 지역 배열(char buf[1<<20])도 프레임을 급격히 키움
  • 깊은 재귀·큰 스택 버퍼가 필요하면 설계를 바꾸거나 힙(15) 검토
  • 문법·종료 조건 감각 → 08 재귀 맛보기
지금은: 프레임 = 한 호출의 작업 공간 · return 시 사라짐 · Call Stack으로 확인. 어셈블리·정확한 x64 레지스터 표는 더 깊게. 프로세스 큰 지도 → 22 · 객체 안 빈 칸 → 27 패딩

27 패딩 · 객체 레이아웃

심화

struct / class 멤버는 메모리에 “적어 넣은 순서 그대로 빈틈 없이”만 놓이지 않습니다. CPU가 편하게 읽도록 정렬(alignment)을 맞추다 보면 사이에 패딩(빈 바이트)이 끼어 sizeof 가 멤버 크기 합보다 커질 수 있습니다.

1. 같은 멤버, 다른 배치 — 그림

흔한 예 (많은 x64 ABI에서): char 정렬 1, int 정렬 4. 숫자는 환경마다 다를 수 있으니 패턴만 보세요.

2. 왜 패딩을 넣나 — 정렬

많은 CPU는 주소가 타입 크기의 배수일 때 읽기·쓰기가 편합니다. (예: 4바이트 int → 주소가 4의 배수)

char 크기 1 · 정렬 1
short 크기 2 · 정렬 2
int / float 크기 4 · 정렬 4
double / 포인터* 크기 8 · 정렬 8 (x64 흔한 경우)

*플랫폼·ABI에 따라 다름. 확인은 sizeof / alignof

  • 멤버 앞에 정렬을 맞추려고 앞 패딩
  • 구조체 전체 정렬을 맞추려고 끝 패딩 (배열에 유리)
  • sizeof(T) ≥ 멤버 크기 합 · 같으면 패딩이 거의 없는 배치

3. 상황 · 코드 · 쓰임

상황: “멤버 합은 6바이트인데 sizeof가 12?”

#include <iostream>

struct A { char a; int b; char c; };
struct B { char a; char c; int b; };

// 많은 PC에서 예:
// sizeof(A) == 12
// sizeof(B) == 8
// alignof(A), alignof(B) 도 함께 보면 감이 옴

int main() {
    std::cout << sizeof(A) << " " << sizeof(B) << "\n";
}

쓰임: 대량 배열·네트워크 패킷 구조·세이브 포맷에서 “생각과 다른 크기”를 설명할 때.

4. 배열이면 패딩이 곱해진다

  • A arr[1000] → 원소마다 패딩 포함 크기
  • 12×1000 vs 8×1000 = 캐시·메모리 차이로 이어질 수 있음 → 24
  • 핫한 큰 배열이면 멤버 순서·타입 선택을 한번 의
  • 가독성 없는 “마이크로 패킹”부터 하지 말 것
// 개념: 원소 stride = sizeof(T)
// 패딩이 클수록 같은 개수에 더 많은 RAM

28 상속 · 가상 함수 · vtable

심화

상속은 타입을 “공통 뼈대 + 특화”로 나눕니다. virtual 이 붙으면 실제 객체 타입에 맞는 함수를 고르고, 그 밑에는 보통 vtable(가상 함수 표)이 있습니다.

관련 메인 11 포인터 12 구조체·클래스 16 스마트 포인터 27 패딩

1. 상속 — is-a 그림

Goblin 은 Enemy 이다 (is-a). 공통 멤버·함수는 베이스에, 특화는 파생에.

Enemy 베이스 · hp, hit() …
▲ 상속 (파생 → 베이스)
Goblin 파생 · 특화 행동
Slime 파생 · 다른 특화

객체 안에는 보통 베이스 멤버 + 파생 멤버가 이어져 놓임 (패딩 규칙은 27)

2. 정적 바인딩 vs 동적 바인딩

virtual 없음 (정적)

포인터 타입(Enemy*)만 보고 함수를 고름. 실제가 Goblin 이어도 베이스 버전이 불릴 수 있음.

virtual 있음 (동적)

실제 객체 타입을 보고 함수를 고름. Enemy* p = new Goblin; 이어도 p->hit() → Goblin::hit.

다형성(polymorphism) 감각: 같은 호출 문장, 다른 실제 동작

3. vtable 감각 — 그림

4. 상황 · 코드 · 쓰임

상황: 적 목록을 베이스 포인터로 돌리며 각자 hit.

struct Enemy {
    int hp = 10;
    virtual void hit(int d) { hp -= d; }
    virtual ~Enemy() = default; // 기반 소멸자는 virtual 권장
};

struct Goblin : Enemy {
    void hit(int d) override { hp -= d * 2; }
};

// Enemy* p = new Goblin;
// p->hit(3);  → Goblin::hit
// delete p;   → 가상 소멸자로 파생까지 정리

쓰임: 스킬/AI 인터페이스, 플러그인식 타입, vector<unique_ptr<Enemy>> 다형 목록.

5. 용어 한 줄

  • override — 베이스 virtual을 덮어씀 (오타 방지에 권장)
  • final — 더 이상 파생/오버라이드 금지 (선택)
  • 순수 가상 = 0 — 인터페이스 뼈대, 추상 클래스
  • 비가상 함수는 “타입 고정 호출”에 가깝고 종종 인라인에 유리
  • 기반 클래스 포인터로 delete 할 때 소멸자가 non-virtual이면 위험

6. 실무 감각 · 비용

복사 베이스만 복사하면 파생이 잘림(object slicing) → 포인터/참조·스마트 포인터로 다루기
다중 상속 가능하지만 복잡도↑. 처음엔 단일 상속 + 인터페이스로 충분한 경우가 많음
기억: 다형으로 쓸 베이스는 virtual ~Base() 를 두는 습관. 안 그러면 delete 경로에서 파생 소멸자가 안 불릴 수 있습니다.
지금은: 상속 = is-a · virtual = 실제 타입으로 호출 · vptr/vtable 모델 · 가상 소멸자. 소유권 → 16 · 소멸/복사/이동 특수 멤버 → 29

29 규칙 오브 파이브 · shared 순환

심화

자원을 직접 소유하는 타입은 소멸·복사·이동을 한 세트로 맞춰야 합니다. 그게 규칙 오브 파이브(Rule of Five) 쪽 이야기입니다. 또 shared_ptr 끼리 서로를 가리키면 참조 카운트가 안 내려가 누수가 납니다 → weak_ptr.

2. 0 · 3 · 5 — 언제 뭘 쓰나

Rule of Zero (권장 기본)

자원을 unique_ptr / vector 등에 맡김. 특수 멤버를 직접 안 씀 — 컴파일러 기본이 충분.

Rule of Three

raw 소유(예: new한 포인터 멤버)를 직접 다루면 소멸·복사생성·복사대입을 같이 맞출 것.

Rule of Five

C++11+ 이동까지 쓰려면 이동 생성·이동 대입도 세트로. 복사를 막을 거면 = delete.

실무 기본선: Zero를 목표 · raw 소유를 직접 쓰기 전에 16·17을 먼저

3. 상황 · 코드 (자원 소유)

상황: 버퍼를 raw로 들고 있던 옛날 스타일 (교육용).

struct Buf {
    int* p;
    int n;
    explicit Buf(int n) : p(new int[n]), n(n) {}
    ~Buf() { delete[] p; }           // 1 소멸

    Buf(const Buf& o)                // 2 복사 생성
      : p(new int[o.n]), n(o.n) {
        for (int i = 0; i < n; ++i) p[i] = o.p[i];
    }
    Buf& operator=(const Buf& o);    // 3 복사 대입 (생략 가능 아님)

    Buf(Buf&& o) noexcept            // 4 이동 생성
      : p(o.p), n(o.n) { o.p = nullptr; o.n = 0; }
    Buf& operator=(Buf&& o) noexcept;// 5 이동 대입
};

한 개만 손대면 기본 생성 규칙이 꼬일 수 있음 → 쓰리/파이브를 의식적으로 맞추거나, Zero로 피하기.

4. Zero로 바꾸는 감각

struct Buf {
    std::vector<int> data;  // 소유·복사·이동을 vector가
    explicit Buf(int n) : data(n) {}
    // 특수 멤버 직접 정의 안 함 → Rule of Zero
};
  • unique_ptr 멤버 → 복사 불가, 이동 가능 (의도에 맞으면 OK)
  • 복사가 필요 없으면 = delete 로 명시
  • “직접 new한 멤버”를 없애는 쪽이 버그가 적음 → 16

5. shared_ptr 순환 — 그림

A가 B를 shared_ptr로, B가 A를 다시 shared_ptr로 잡으면 서로 refcount가 1 이하로 안 떨어져 영원히 안 지워짐.

순환 (누수)

Node A use_count ≥ 1
shared ↔ shared
Node B use_count ≥ 1

외부 핸들을 버려도 서로가 붙잡고 있어 소멸자 안 불림.

한쪽 weak (해결 감각)

Parent 소유 shared
shared → · ← weak
Child 관찰 weak

부모→자식은 소유, 자식→부모는 weak_ptr로 관찰만.

부모-자식·양방향 그래프·캐시 콜백에서 자주 등장

6. 상황 · 코드 (순환 끊기)

상황: 트리 노드가 부모를 다시 가리킨다.

struct Node {
    std::shared_ptr<Node> child;   // 소유
    std::weak_ptr<Node> parent;  // 비소유 관찰
};

auto p = std::make_shared<Node>();
auto c = std::make_shared<Node>();
p->child = c;
c->parent = p;   // weak — 순환 끊김

// parent.lock() 으로 잠시 shared 확보 가능
if (auto up = c->parent.lock()) {
    // up 사용…
}

쓰임: UI 위젯 트리, 씬 그래프, 옵저버가 subject를 약하게 붙들 때.

7. 실무 체크

  • 기본 소유: unique_ptr (16)
  • 공유가 진짜 필요할 때만 shared_ptr
  • 역방향·캐시·“있을 수도” → weak_ptr
  • 특수 멤버를 하나 쓰면 나머지도 의도를 밝혀라 (= default / = delete)
  • 복사 생성만 대충 만들고 대입·소멸을 잊기

30 const · 바꾸지 않겠다는 약속

const = “이 값은 여기서 안 바꾼다”는 약속을 컴파일러에게 거는 것. 어기면 컴파일 단계에서 막아 줍니다. 실수를 실행 전에 잡는 안전벨트.
변수(05) · 참조(11) · 멤버 함수(08)와 함께 보면 좋습니다.

가장 기본 — 상수 변수

const int MAX_HP = 100;   // 고정 값
MAX_HP = 120;             // ✗ 컴파일 에러: const는 못 바꿈

int level = 5;            // 이건 자유롭게 변경 가능
level = 6;                // ✓
  • “절대 안 변할 값”엔 const를 붙여 의도를 코드에 남김
  • 누가 실수로 바꾸면 컴파일러가 대신 잡아 줌
  • 매직 넘버 대신 이름 붙은 상수로 → 읽기 쉬움

상황 · 코드 · 쓰임 — 안 바꿀 인자는 const 참조로

상황: 큰 객체를 함수에 넘길 때 복사는 비싸다. 참조로 넘기되 “안 건드린다”를 약속.

// 복사 없이(참조) + 안 바꿈(const) → 안전하고 빠름
void printName(const std::string& name) {
    std::cout << name << "\n";
    // name = "hi";   // ✗ const라 수정 불가 — 실수 차단
}

쓰임: 읽기만 하는 함수 인자의 사실상 기본형. const T&는 “복사 안 함 + 안 바꿈”. 참조 자세히 → 11

포인터와 const — 읽는 법은 오른쪽 → 왼쪽

*를 기준으로 왼쪽이 const면 가리키는 값이, 오른쪽이 const면 포인터 자신이 고정됩니다.

선언읽기못 바꾸는 것
const int* pp는 const int를 가리킴*p (값)
int* const pp는 int를 가리키는 const 포인터p (주소)
const int* const p둘 다 const*p와 p 모두
팁: 헷갈리면 선언을 오른쪽부터 읽어 보세요. int* const p → “p는 / const / int로의 포인터”. 포인터·주소 개념 → 11

const 멤버 함수 — “이 함수는 객체를 안 바꾼다”

struct Player {
    int hp = 100;
    int getHp() const {      // const: 멤버를 수정하지 않음을 보장
        return hp;
        // hp = 0;           // ✗ const 함수 안에서는 멤버 변경 불가
    }
};

const Player p;
p.getHp();   // ✓ const 객체는 const 함수만 호출 가능

쓰임: getter처럼 “읽기만” 하는 멤버엔 const를 붙이는 게 표준. 함수·멤버 → 08 · 클래스 → 12

한 걸음 더 — constexpr: constexpr int N = 8*8;처럼 컴파일 타임에 계산되는 상수. 배열 크기 등에 쓰면 런타임 비용 0. 지금은 “const의 컴파일 타임 강화판” 정도로만 알아 두면 충분합니다.
지금은 여기까지: “안 바꾼다는 약속을 컴파일러가 지켜 준다”. const 정확성(const-correctness)을 코드 전반에 퍼뜨리는 감각은 쓰면서 자연스럽게 붙습니다.

상황 · 코드 · 쓰임 — map: 키 → 값

상황: 아이템 이름별 개수를 세고 싶다. 인덱스(0,1,2…) 말고 “이름”으로 찾기.

#include <map>

std::map<std::string, int> inv;   // 이름 → 개수
inv["potion"] += 1;               // 없으면 0에서 시작해 +1
inv["potion"] += 1;
inv["sword"]   = 1;

for (auto& [name, cnt] : inv) {    // 키·값 한 번에 꺼내기

}

쓰임: 인벤토리 집계, ID→객체 조회, 이름표. 순서가 필요 없으면 더 빠른 std::unordered_map도 있음.

반복자(iterator) — 컨테이너를 훑는 공통 손잡이

모든 컨테이너는 begin()(첫 원소)와 end()(끝 다음)를 줍니다. 범위 for는 사실 이 반복자를 감싼 편의 문법이에요.

std::vector<int> v = {10, 20, 30};

for (auto it = v.begin(); it != v.end(); ++it) {
    std::cout << *it << "\n";   // *it = 지금 가리키는 값
}

for (int x : v) { }   // ↑ 위와 같은 일 (범위 for)

쓰임: <algorithm> 함수들이 이 begin/end 쌍을 받아 동작합니다. 범위 for → 07

상황 · 코드 · 쓰임 — <algorithm>: 정렬·탐색

상황: 점수를 내림차순 정렬하고, 특정 값이 있는지 찾기.

#include <algorithm>
#include <vector>

std::vector<int> s = {90, 70, 100, 80};

std::sort(s.begin(), s.end());                 // 오름차순: 70 80 90 100
std::sort(s.begin(), s.end(), std::greater<>()); // 내림차순: 100 90 80 70

auto it = std::find(s.begin(), s.end(), 90);
bool found = (it != s.end());                  // 90 있나?
int n = std::count(s.begin(), s.end(), 80);    // 80이 몇 개?

쓰임: 랭킹 정렬, 아이템 검색, 조건 개수 세기. 직접 for로 짜지 말고 표준 함수를 먼저 찾아보세요 — 검증돼 있고 빠릅니다.

32 재할당 · 이터레이터 무효화 · span

심화

vector(14)·31에서 미룬 속사정. vector가 커질 때 무슨 일이 벌어지는지, 왜 그때 이터레이터·포인터·참조가 깨지는지, 그리고 소유하지 않고 “빌려 보는” std::span.

한눈에 보기 — capacity 초과 → 재할당

size가 capacity에 닿은 상태에서 push_back하면, vector는 더 큰 새 버퍼를 잡아 값을 옮기고 옛 버퍼를 버립니다.

옛 버퍼의 값이 새 버퍼로 옮겨진 뒤 옛 버퍼는 해제됩니다. 이때 옛 주소를 들고 있던 손잡이는 전부 못 쓰게 됩니다.

상황 · 코드 · 쓰임 — 무효화가 버그를 만드는 순간

상황: 원소를 가리키는 포인터를 들고 있는데, 그 사이 push_back으로 재할당이 일어남.

std::vector<int> v = {90, 80, 100};   // size==3, capacity==3(가정)
int* p = &v[0];         // 첫 원소 주소를 보관

v.push_back(70);        // capacity 초과 → 재할당 → 값들이 새 버퍼로 이사
std::cout << *p;        // ✗ p는 옛 버퍼(이미 해제)를 가리킴 = 댕글링

쓰임: “컨테이너를 바꾸는 동안 그 원소의 주소/이터레이터를 들고 있지 않기”. 들어야 한다면 인덱스를 저장하세요(재할당돼도 v[i]는 유효). 스택·힙·댕글링 → 10·15

reserve() — 재할당을 미리 막기

std::vector<int> v;
v.reserve(1000);   // 미리 1000칸 확보
int* p = &v[0];    // 이후 1000개까지는
for (int i=0;i<1000;++i)
    v.push_back(i); // 재할당 없음 → p 유효

쓰임: 넣을 개수를 대충 알면 reserve로 재할당·복사 비용과 무효화 위험을 함께 줄임.

상황 · 코드 · 쓰임 — std::span: 소유 안 하는 뷰

상황: “연속된 원소 묶음”을 읽는 함수 하나로 vector·array·C 배열을 전부 받고 싶다. 복사 없이.

#include <span>

// span = {시작 포인터 + 길이}. 데이터를 소유하지 않고 빌려 봄 (C++20)
int sum(std::span<const int> xs) {
    int s = 0;
    for (int x : xs) s += x;   // 일반 범위 for 그대로
    return s;
}

std::vector<int> v = {1, 2, 3};
int arr[] = {4, 5, 6};
sum(v);     // vector 그대로
sum(arr);   // C 배열 그대로 — 복사 없음

쓰임: 함수 인자로 “연속 메모리 구간”을 받을 때 컨테이너 종류에 안 묶이게. 단, 원본이 살아 있는 동안만 유효 — 재할당·수명 종료 시 span도 댕글링. 참조 감각 → 11

지금은 여기까지: “컨테이너를 바꾸면 그 안을 가리키던 손잡이는 의심하라”. 핵심 방어책은 인덱스 저장 · reserve · 순회 중 수정 금지 세 가지입니다.

33 람다 · 함수 포인터

심화

함수를 값처럼 넘기는 세 가지 방법. 즉석에서 만드는 람다(lambda), 예전부터 있던 함수 포인터, 그리고 무엇이든 담는 상자 std::function. algorithm(31)에 조건을 끼워 넣을 때 특히 유용합니다.

람다 — 이름 없이 그 자리에서 만드는 함수

auto add = [](int a, int b) { return a + b; };
int r = add(2, 3);   // 5

구성은 [캡처](매개변수){ 본문 }. 대괄호 []가 람다의 표식이자 바깥 변수를 끌어오는 캡처 목록입니다.

[캡처] (매개변수) { 본문 }

바깥 변수 끌어오기 · 입력 · 할 일 — 왼쪽부터 이 순서.

캡처 — 바깥 변수를 어떻게 데려오나

int base = 10;

auto byVal = [base](int x){ return x + base; };  // 값 복사(그때의 10 고정)
auto byRef = [&base](int x){ return x + base; }; // 참조(현재 base를 봄)

base = 99;
byVal(1);  // 11  (복사해 둔 10)
byRef(1);  // 100 (지금의 99)
캡처뜻
[x]x를 값으로 복사
[&x]x를 참조로

상황 · 코드 · 쓰임 — algorithm에 조건 끼우기

상황: 기준을 바꿔 정렬하거나, 조건에 맞는 것만 세고 싶다.

#include <algorithm>
#include <vector>

std::vector<int> hp = {30, 100, 55, 80};

// 내림차순 정렬 — 비교 규칙을 람다로
std::sort(hp.begin(), hp.end(),
          [](int a, int b){ return a > b; });

// 50 넘는 것만 세기 — 조건을 람다로

                          [](int h){ return h > 50; });

쓰임: 정렬 기준, 필터 조건, 콜백. “규칙 한 조각”을 그 자리에서 함수로 넘기는 게 람다의 본업입니다.

함수 포인터 — 예전 방식

int add(int a, int b){ return a+b; }

// 캡처 없는 람다는 함수 포인터로도 변환됨

    [](int a,int b){ return a+b; };

쓰임: C API 콜백 등록 등. 상태(캡처)를 못 담는 게 한계.

op = [](int a,int b){return a*b;}; // 람다(캡처 OK)

34 CPU 내부 — 두뇌를 열어보면

컴퓨터

02에서 CPU를 “두뇌”라고만 했죠. 그 안엔 계산하는 부분(ALU), 지휘하는 부분(제어장치), 가장 빠른 저장소(레지스터)가 있고, 클럭이라는 박자에 맞춰 명령을 하나씩 처리합니다.

한눈에 보기 — CPU 블록도

CPU는 버스(bus)로 RAM과 값을 주고받습니다. 자주 쓰는 값은 안쪽 캐시에 둬서 느린 RAM 왕복을 줄입니다.

제어장치가 명령을 읽어 ALU에 시키고, 값은 레지스터·캐시에 두며, 부족하면 버스로 RAM을 오갑니다.

레지스터 — 왜 이렇게 빠른가

레지스터는 CPU 안에 있는 손바닥만 한 저장소. 개수는 적지만(수십 개) 접근이 압도적으로 빠릅니다. 변수·연산 값이 잠깐 여기 올라와 계산됩니다.

클럭 · 파이프라인

클럭은 초당 박자 수(3.5 GHz = 35억/초). 한 명령은 대략 네 단계를 거칩니다.

파이프라인 = 세탁기·건조기처럼 단계를 겹쳐 돌려 처리량을 올리는 기법. 한 명령이 실행될 때 다음 명령은 벌써 해독 중.

코어 · 스레드

  • 코어 = 독립적으로 명령을 실행하는 일꾼. 4코어 = 진짜 동시에 4가지
  • 하드웨어 스레드(하이퍼스레딩) = 코어 하나가 노는 시간을 활용해 두 흐름을 번갈아 — 완전한 2배는 아님
  • 프로그램의 스레드는 이 위에서 OS가 번갈아 얹어 돌림

동시성의 소프트웨어 쪽 → 심화(예정)

지금은 여기까지: CPU = 제어장치·ALU·레지스터가 클럭 박자로 명령을 처리하고, 느린 RAM은 캐시로 감춘다. 이 그림 하나면 “왜 캐시·지역성이 중요한가”가 자연스럽게 이어집니다.

휘발성 — 전원을 끄면?

휘발성(volatile) = 전원이 끊기면 내용이 사라짐. RAM이 대표. 그래서 “저장” 버튼은 휘발성 RAM의 값을 비휘발성 디스크로 옮기는 일입니다.

RAM vs ROM

  • RAM: 읽고 쓰기 자유·빠름·휘발성 → 작업 공간
  • ROM: 주로 읽기·비휘발성 → 펌웨어·부팅 코드
  • 이름의 “Random Access”는 아무 위치나 바로 접근한다는 뜻(순차 테이프의 반대)

SSD vs HDD

  • SSD: 반도체(플래시)·움직이는 부품 없음·빠름
  • HDD: 회전 원판+헤드·느리지만 대용량당 저렴
  • 둘 다 RAM보다는 훨씬 느림 — 그래서 자주 쓸 값은 RAM/캐시로
지금은 여기까지: “빠른 건 작고 사라지고(RAM), 큰 건 느리고 남는다(디스크)”. 프로그램이 다루는 변수는 휘발성 RAM 위 — 이 감각이 파일 저장·캐시·성능의 밑그림입니다.

왜 오차가 생기나 — 0.1은 2진수로 무한소수

10진 0.1은 2진수로 0.0001100110011…처럼 끝없이 반복합니다. (10진에서 1/3 = 0.333…이 안 끝나는 것과 같은 이치.) 유한한 비트에 담으려면 잘라야 하고, 그 순간 미세 오차가 생깁니다.

#include <iostream>
#include <iomanip>

double a = 0.1 + 0.2;
std::cout << std::setprecision(17) << a;
// 0.30000000000000004  ← 0.3이 아니라 근사값

std::cout << (a == 0.3);   // 0 (false!)

상황 · 코드 · 쓰임 — 실수는 “==” 대신 오차 허용 비교

상황: 두 실수가 “사실상 같은지” 확인. 정확히 같길 바라면 안 됨.

#include <cmath>

bool nearlyEqual(double x, double y, double eps = 1e-9) {
    return std::fabs(x - y) < eps;   // 차이가 아주 작으면 같다고 본다
}

nearlyEqual(0.1 + 0.2, 0.3);   // true

쓰임: 물리·좌표·시간 누적 계산. 돈처럼 정확해야 하면 실수 대신 정수(센트 단위)나 고정소수점을 쓰세요. 비트 감각 → 정수 표현(37)

float vs double

타입비트유효숫자(10진)
float32약 7자리
double64약 15~16자리

기본은 double. 메모리·대역폭이 빠듯한 대량 데이터에만 float.

흔한 함정

  • 실수 == 정확 비교
  • 돈 계산을 double로 (반올림 누적 오차)
  • 큰 수 + 아주 작은 수 → 작은 쪽이 묻힘(흡수 오차)
  • 누적 합은 순서·방식에 따라 결과가 달라질 수 있음
지금은 여기까지: 실수는 근사값이다. 화면 표시용으론 충분하지만 비교는 오차 허용으로, 돈은 정수로. “왜 0.1+0.2가 0.3이 아니냐”에 답할 수 있으면 충분합니다.

39 문자 인코딩 · ASCII · 유니코드 · UTF-8

컴퓨터

컴퓨터는 글자도 숫자로 저장합니다. 'A'는 65. 영어만 담던 ASCII에서, 세상 모든 글자에 번호를 준 유니코드, 그 번호를 바이트로 담는 UTF-8까지의 이야기.

ASCII — 영문·기호를 1바이트로

가장 오래된 규칙. 0~127번에 영문 대소문자·숫자·기호를 배치. char(09) 한 칸에 딱 들어갑니다.

char c = 'A';
int  n = c;        // 65  (문자는 사실 숫자)
char d = 'A' + 1;  // 'B' (66)

// '0'~'9'는 48~57, 'a'는 97 → 소문자/대문자 변환에 이용

쓰임: 문자↔숫자 변환, 대소문자 바꾸기, 파싱. 단 한글·이모지는 못 담음(128칸뿐).

유니코드 → UTF-8 — 번호를 바이트로

유니코드는 모든 글자에 번호(코드포인트, 예 U+AC00=‘가’)를 매깁니다. UTF-8은 그 번호를 1~4바이트로 담는 방식 — ASCII는 그대로 1바이트라 호환됩니다.

A → U+0041 → 0x41 1바이트
가 → U+AC00 → EA B0 80 3바이트

영문은 1바이트, 한글은 보통 3바이트, 이모지는 4바이트. 그래서 UTF-8은 가변 길이.

상황 · 코드 · 쓰임 — “한글 한 글자가 왜 3?”

상황: std::string은 바이트의 열입니다. 그래서 .size()는 글자 수가 아니라 바이트 수.

#include <string>

std::string s = "가";
s.size();      // 3  (글자 1개지만 UTF-8로 3바이트)

std::string e = "Hi";
e.size();      // 2  (ASCII라 1바이트씩)

쓰임: 파일·네트워크는 거의 UTF-8. “글자 수”가 필요하면 바이트가 아니라 코드포인트로 세야 함(라이브러리 사용). 소스 파일도 UTF-8로 저장하면 한글 깨짐이 줄어듭니다. 문자 기본 → 09

흔한 함정

  • 한글 문자열에서 s.size()를 글자 수로 착각
  • 바이트 중간을 잘라 글자 깨뜨리기
  • 콘솔에 한글이 깨지면 인코딩(코드페이지) 설정 확인
  • 파일·소스는 UTF-8 통일
지금은 여기까지: 글자 = 번호(유니코드) → 바이트(UTF-8). 영문 1, 한글 3, 이모지 4바이트. std::string은 바이트 열이라는 것만 기억하면 대부분의 “깨짐·길이” 문제가 풀립니다.

40 힙 관리 · 단편화 · 할당자

컴퓨터

new/delete(15)가 실제로 하는 일. 힙(10)에는 할당자(allocator)가 있어 빈 공간을 관리합니다. 반복해 빌리고 반납하다 보면 빈 자리가 잘게 흩어지는(단편화) 문제가 생기고, 그래서 힙 할당은 공짜가 아닙니다.

할당자 — 빈 조각 목록에서 맞는 걸 찾아줌

new를 부르면 할당자가 비어 있는 조각 목록(free list)에서 요청 크기에 맞는 자리를 찾아 내어 줍니다. delete는 그 자리를 다시 목록에 되돌리고, 가능하면 옆의 빈 조각과 합칩니다(병합).

  • new = 맞는 빈 조각 탐색 + 표시
  • delete = 반납 + 인접 빈 조각 병합
  • 스택(10)은 그냥 포인터만 올렸다 내리면 끝 — 그래서 힙보다 훨씬 쌈

왜 힙이 비싼가

  • 빈 조각을 탐색해야 함
  • 여러 스레드가 동시에 쓰면 락 필요
  • 가끔 OS에 더 달라고 시스템 콜

  • 작은 문자열은 SSO로 힙 없이 내부 버퍼에 담기도 함

지금은 여기까지: 힙 = 할당자가 빈 조각을 관리하는 공간. 반복 할당/해제는 단편화를 부르고 할당 자체가 비용이다. 덩어리로 잡고 재사용이 핵심 처방 — 스택·vector·풀을 먼저 떠올리세요.

41 프로세스 · 스레드 · 스케줄링

컴퓨터

실행 중인 프로그램의 단위. 프로세스는 독립된 메모리를 가진 한 채의 집, 스레드는 그 집 안에서 동시에 움직이는 여러 일꾼. OS는 이들을 CPU 코어(34)에 번갈아 얹어 돌립니다.

한눈에 보기 — 한 프로세스, 여러 스레드

스레드들은 코드·힙·전역을 공유하고, 스택과 실행 위치(PC·레지스터)만 각자 가집니다.

공유가 많아 스레드는 통신이 쉽지만, 같은 데이터를 동시에 건드리는 위험도 함께 생깁니다(→ 42).

프로세스 vs 스레드

프로세스스레드

컨텍스트 스위칭

코어 수보다 실행 흐름이 많으면 OS가 번갈아 실행합니다. 바꿀 때 현재 스레드의 레지스터·PC를 저장하고 다음 것을 복원 — 이 전환 비용이 공짜가 아닙니다.

  • 너무 많은 스레드 = 전환 오버헤드↑
  • 보통 코어 수 근처가 효율적

스케줄링 — 누구에게 CPU를 줄까

스케줄러(OS)가 준비된 스레드들에게 짧은 시간씩 CPU를 나눠 줍니다. 그래서 코어가 4개여도 프로그램 수십 개가 동시에 돌아가는 것처럼 보입니다(가상 메모리(23)가 각자 독립 주소를 주는 것과 짝).

쓰임: “왜 sleep이 정확히 안 맞나”, “왜 실행마다 순서가 조금 다르나”의 답. 실행 순서에 의존하는 코드는 위험 → 동기화(42) 필요.

지금은 여기까지: 프로세스=독립 메모리, 스레드=공유 메모리 위 여러 흐름. OS가 컨텍스트 스위칭으로 번갈아 돌린다. 공유의 편함 뒤엔 동시 접근 위험이 따라오며, 그게 다음 장입니다.

42 동시성 · 경쟁 상태 · 락 · 데드락

컴퓨터

여러 스레드(41)가 같은 데이터를 동시에 건드리면 값이 꼬입니다(경쟁 상태). 락으로 한 번에 하나만 들어가게 막지만, 락을 잘못 쓰면 서로 기다리다 멈추는 데드락이 생깁니다.

동시성 vs 병렬성

동시성(concurrency)병렬성(parallelism)
뜻여러 일을 번갈아 다룸여러 일을 진짜 동시에
필요코어 1개로도 가능코어 여러 개 필요
비유요리사 1명이 여러 냄비를 오감요리사 여러 명이 각 냄비

둘 다 “공유 데이터를 여럿이 만진다”는 문제는 똑같이 안고 있습니다.

상황 · 코드 · 쓰임 — 경쟁 상태(race condition)

상황: 두 스레드가 같은 counter를 동시에 +1. counter++는 사실 읽기→더하기→쓰기 세 단계라, 사이에 끼어들면 한 번이 유실됩니다.

int counter = 0;   // 두 스레드가 공유

// 스레드 A, B가 각각 counter++ 를 100만 번
// 기대: 200만 → 실제: 그보다 작을 때가 있음

// counter++ 분해:
//   1) tmp = counter   (읽기)
//   2) tmp = tmp + 1    (더하기)
//   3) counter = tmp    (쓰기)   ← 겹치면 한쪽 갱신이 덮여 사라짐

쓰임: 공유 카운터·리스트·플래그. 겹쳐 쓰면 “가끔” 틀리는 재현 어려운 버그가 됩니다. 실행마다 결과가 다르면 경쟁 상태를 의심.

락(mutex)으로 보호

std::mutex m;

void inc() {
    std::lock_guard<std::mutex> g(m);
    // ↑ 여기부터 임계 구역: 한 번에 한 스레드만
    counter++;          // 안전
}   // g 소멸 → 자동 unlock (RAII)

임계 구역 = 한 번에 하나만 들어가야 하는 코드 구간. C++ 스레드 API 자세히 → 동시성 심화(예정)

주의 — 락의 대가

  • 너무 넓게 잠그면 사실상 순차 실행(병렬 이득↓)
  • 잠그는 걸 잊으면 경쟁 상태 그대로
  • 가장 좋은 건 공유를 줄이기(각자 계산 후 합치기)

데드락 — 서로가 서로를 기다림

두 스레드가 락을 반대 순서로 잡으면, 각자 상대가 쥔 락을 기다리며 영원히 멈춥니다(순환 대기).

화살표가 고리를 이루면 아무도 못 나아감. 예방책: 모든 스레드가 락을 같은 순서로 잡기.

지금은 여기까지: 공유 데이터 동시 수정 = 경쟁 상태 → 락으로 임계 구역 보호 → 락 순서 어긋나면 데드락. 제일 안전한 길은 공유 자체를 줄이는 설계입니다. C++ 도구(thread·mutex·atomic)는 동시성 심화에서.

43 시스템 콜 · 커널 / 유저 모드

컴퓨터

내 프로그램은 디스크·화면·네트워크 같은 장치를 직접 만질 수 없습니다. 대신 운영체제(커널)에게 “해 달라”고 부탁하는데, 그 요청이 시스템 콜. 평소 코드는 권한이 낮은 유저 모드, 커널만 커널 모드로 특권 작업을 합니다.

한눈에 보기 — 유저 ↔ 커널

유저 코드가 syscall로 커널에 요청 → 커널이 장치를 다루고 결과를 돌려줌. 이 모드 전환에 비용이 듭니다.

왜 이렇게 나눴나 — 보호

  • 한 프로그램의 실수가 다른 프로그램·OS를 못 망가뜨리게 격리
  • 장치 접근을 커널이 중재해 충돌·보안 문제 차단
  • 그래서 잘못된 포인터 접근은 유저 모드에서 즉시 차단(세그폴트)

가상 메모리(23)로 각 프로그램에 독립 주소를 주는 것과 한 쌍의 보호 장치입니다.

익숙한 것들의 정체

내가 쓴 코드속에서 부르는 것
std::cout (04)write 계열 syscall
파일 읽기/쓰기open·read·write
큰 new (15)가끔 mmap/sbrk

왜 느린가

  • 유저→커널 모드 전환 비용
  • 그래서 출력·파일 I/O는 모아서(버퍼링) 한 번에
  • "\n" 잦은 flush보다 버퍼가 유리할 때가 많음
지금은 여기까지: 특권 작업은 전부 커널에게 시스템 콜로 부탁한다. 유저/커널 모드 분리는 보호 장치이자 I/O가 비싼 이유. “출력·파일은 모아서”가 여기서 나오는 실전 감각입니다.

44 파일시스템 기초

컴퓨터

디스크(35)의 바이트 더미를 이름·폴더로 정리해 주는 층. 파일은 결국 바이트 열 + 메타데이터이고, 경로로 찾아갑니다. 접근은 전부 커널의 시스템 콜(43)로 일어나죠.

한눈에 보기 — 디렉터리 트리와 경로

폴더(디렉터리) 안에 폴더·파일이 겹겹이. 루트에서부터의 길이 절대 경로, 지금 위치 기준이 상대 경로.

C:\  (루트)
├─ Users\
│  └─ me\
│     ├─ game.cpp        ← 상대경로:  game.cpp
│     └─ save\
│        └─ slot1.dat    ← 절대경로:  C:\Users\me\save\slot1.dat
└─ Windows\

Windows는 \, macOS·리눅스는 /로 구분. C++ 문자열에선 \\ 또는 /를 씁니다.

파일 = 바이트 + 메타데이터

  • 내용: 그냥 바이트 열(39)
  • 메타데이터: 크기·수정 시각·권한·이름
  • 확장자(.cpp·.png)는 힌트일 뿐 — 내용을 강제하진 않음

텍스트 vs 바이너리

  • 텍스트: 사람이 읽는 글자(인코딩 적용) — 소스·설정·로그
  • 바이너리: 값 그대로의 바이트 — 이미지·실행파일·세이브
  • 바이너리를 텍스트 편집기로 열면 깨져 보이는 이유

상황 · 코드 · 쓰임 — 파일 읽고 쓰기

상황: 점수를 파일에 저장하고 다시 읽기. <fstream>이 cout(04)과 똑같은 <</>>를 파일에 씁니다.

#include <fstream>
#include <string>

// 쓰기
std::ofstream out("save.txt");
out << "score " << 1200 << "\n";
// out 소멸 시 자동으로 닫힘(flush) — RAII

// 읽기
std::ifstream in("save.txt");
std::string key; int value;
in >> key >> value;   // "score", 1200

쓰임: 세이브 파일, 설정, 로그, 데이터 입출력. 파일이 없거나 권한이 없으면 열기 실패 → 항상 if (in)로 확인. 모던 경로 처리는 <filesystem> → 유틸 심화(예정)

지금은 여기까지: 파일 = 바이트 + 메타데이터, 경로로 찾고, fstream으로 읽고 쓴다. 내용·확장자·인코딩은 별개라는 감각이면 충분합니다. 실제 접근은 커널(43)이 대신합니다.

45 어셈블리 · 기계어 · 컴파일 파이프라인

컴퓨터

우리가 쓴 C++는 결국 CPU가 아는 기계어(0/1)가 됩니다. 그 사이에 사람이 그나마 읽을 수 있는 어셈블리가 있고요. 컴파일(03)의 끝단에서 무슨 일이 벌어지는지 봅니다.

한눈에 보기 — 소스에서 실행파일까지

전처리·컴파일 → 어셈블 → 링크. 앞의 03이 “왜 헤더/분할 컴파일”인지였다면, 여기는 “컴파일러가 뱉는 결과물”입니다.

같은 함수, 세 얼굴

덧셈 함수 하나가 어셈블리에서는 이렇게 보입니다(x86-64 개략). 명령 하나하나가 레지스터(34)를 다룹니다.

C++

int add(int a, int b) {
    return a + b;
}

어셈블리 (개략)

add:
    mov eax, edi   ; a를 eax로
    add eax, esi   ; eax += b
    ret            ; eax를 반환

기계어는 이 어셈블리를 바이트로 바꾼 것(예: 01 F0). CPU는 이 바이트만 읽습니다.

디스어셈블 — 거꾸로 읽기

  • 기계어(.o/.exe)를 다시 어셈블리로 풀어 보는 것
  • objdump -d, 또는 온라인 Compiler Explorer(godbolt)
  • “컴파일러가 내 코드를 어떻게 바꿨나” 확인·최적화 학습에

왜 알아 두나

  • 최적화가 무엇을 지웠는지·인라인했는지 보임
  • UB·크래시 디버깅의 마지막 단서
  • 평소엔 몰라도 되지만, 성능·버그의 바닥에서 만남
지금은 여기까지: C++ → 어셈블리(사람이 읽는 명령) → 기계어(바이트). 컴파일러가 이 변환을 하고, 디스어셈블로 거꾸로도 볼 수 있다. 매일 쓸 지식은 아니지만 “바닥에 뭐가 있는지”를 알면 두렵지 않습니다.

  • OS 로더가 이걸 읽어 메모리에 펼치고 실행 시작

ABI — 컴파일된 코드끼리의 약속

ABI(Application Binary Interface)는 바이너리 수준의 규칙 모음입니다. 함수 인자를 어느 레지스터로 넘길지(호출 규약(26)), 이름을 어떻게 바꿀지(맹글링), 구조체를 어떻게 배치할지(패딩(27)) 같은 것.

  • 같은 ABI면 서로 다른 곳에서 컴파일된 코드도 연결되어 동작
  • 컴파일러·버전·설정이 달라 ABI가 어긋나면 이상한 크래시
  • 그래서 라이브러리는 보통 같은 툴체인·설정으로 맞춰 빌드

쓰임: “왜 이 .dll을 못 쓰지”, “왜 디버그/릴리즈 라이브러리를 섞으면 터지지”의 답이 ABI에 있습니다.

지금은 여기까지: 링크로 라이브러리를 넣거나(정적) 참조하거나(동적), 결과는 PE/ELF 실행파일, 그 코드끼리의 바이너리 약속이 ABI. 배포·“DLL 없음”·툴체인 섞임 문제의 뿌리입니다.

47 복잡도 · Big-O

컴퓨터

“이 코드 빠른가?”를 초 단위가 아니라 입력이 커질 때 얼마나 더 일하나로 봅니다. 그 표기가 Big-O. 상수는 무시하고 성장 추세만 보는 게 요령이에요. 정렬·탐색(31)을 고를 때 바로 쓰입니다.

한눈에 보기 — 성장 곡선

입력 n이 커질수록 연산 수가 어떻게 늘어나는지. 위로 가파를수록 나쁩니다.

O(1) O(log n) O(n) O(n log n) O(n²)

커질수록 벌어진다 — n에 따른 연산 수(개략)

복잡도n=10n=1,000대표 예
O(1) 상수11배열 인덱스 v[i]
O(log n) 로그~3~10이진 탐색
O(n) 선형101,000전체 한 번 훑기
O(n log n)~33~10,000좋은 정렬(sort)
O(n²) 제곱1001,000,000이중 for 비교

핵심: n이 작으면 다 비슷. n이 커질 때 O(n²)가 폭발합니다. 그래서 큰 데이터엔 곡선의 “기울기”가 전부.

코드로 감 잡기

v[i];                 // O(1)  — 바로 접근

for (x : v) use(x);   // O(n)  — 한 번 훑기

for (a : v)           // O(n²) — 훑기 안에 훑기
  for (b : v) cmp(a,b);

// 정렬된 데이터에서 이진 탐색 → O(log n)

실전 감각

  • 중첩 루프가 보이면 O(n²) 의심 → 규모 클 때 위험
  • map/set·정렬로 O(n²)를 O(n log n)로 낮추기
  • 상수·작은 n에선 “단순한 게” 더 빠를 때도 많음
  • 최악·평균을 구분(해시는 평균 O(1), 최악 O(n))
지금은 여기까지: Big-O = 입력이 커질 때의 성장 추세. O(1)<O(log n)<O(n)<O(n log n)<O(n²). “중첩 루프를 줄이고, 자료구조로 탐색을 낮춘다”가 대부분의 최적화입니다. 자료구조는 다음 장(48).

그래프는 점(노드)들이 선(엣지)으로 이어진 구조. 지도·친구 관계·의존성처럼 “무엇이 무엇과 연결되나”를 담습니다. 트리는 사실 사이클 없는 그래프의 한 종류.

쓰임: 길찾기(최단 경로), 추천, 빌드 의존성. 표현은 인접 리스트(vector<vector<int>>)나 인접 행렬.

51 함수 더 · 오버로딩 · 디폴트 인자 · inline

C++

함수(08)의 실전 확장 셋. 같은 이름을 인자만 바꿔 여럿 두는 오버로딩, 인자를 생략하면 채워 주는 디폴트 인자, 헤더에 정의를 둘 수 있게 해 주는 inline.

상황 · 코드 · 쓰임 — 오버로딩(같은 이름, 다른 인자)

상황: 하는 일은 같은데 받는 타입이 다르다. 이름을 하나로 통일하고 인자로 구분.

int    add(int a, int b)       { return a + b; }
double add(double a, double b) { return a + b; }   // 같은 이름, 다른 타입

add(2, 3);       // int 버전
add(2.5, 3.5);   // double 버전 — 컴파일러가 인자 보고 고름

쓰임: print(int)·print(string)처럼 자연스러운 API. 연산자 오버로딩(13)도 같은 원리.
주의: 반환 타입만 다른 건 오버로딩이 안 됩니다(인자로 구분 불가).

디폴트 인자

void spawn(int hp, int lvl = 1) {
    // lvl 생략 시 1
}

spawn(100);      // lvl = 1
spawn(100, 5);   // lvl = 5
  • 자주 쓰는 값을 기본으로 → 호출이 간결
  • 기본값은 뒤쪽 인자부터만
  • 선언(헤더)에 한 번만 적기

오버로딩 vs 디폴트

  • 인자 타입이 다르면 → 오버로딩
  • 인자 개수만 다르고 로직 같으면 → 디폴트 인자
  • 둘을 섞어 모호해지면 컴파일 에러(어느 걸 부를지 불명확)

inline — 요즘의 진짜 의미

원래는 “함수 호출을 펼쳐 넣어 호출 비용을 없애 달라”는 힌트였습니다. 요즘 컴파일러는 알아서 판단하므로, 실무에서 inline의 핵심 의미는 “이 정의를 여러 파일에 넣어도 된다”(중복 정의 허용, ODR 예외)입니다.

// 헤더에 함수 정의를 두고 여러 .cpp가 include 해도 OK
inline int square(int x) { return x * x; }
  • 헤더 전용(header-only) 유틸 함수에 유용 — 헤더/분할 컴파일(03)
  • 클래스 안에 정의한 멤버 함수는 자동으로 inline 취급
  • 성능을 위해 일부러 붙일 필요는 거의 없음(컴파일러가 더 잘 판단)
지금은 여기까지: 오버로딩=이름 하나에 여러 인자 버전, 디폴트 인자=생략 시 기본값, inline=헤더에 정의 허용. 반환 타입만 다른 오버로딩은 불가, 기본값은 뒤 인자부터 — 이 두 함정만 피하면 됩니다.

52 배열 · 문자열 더

C++

배열·문자열(09)의 실전 보강. 2차원 배열, C 문자열의 함정, 그리고 std::string의 자주 쓰는 멤버와 string_view 맛보기. 늘어나는 목록은 여전히 vector(14)가 먼저입니다.

2차원 배열 — 격자·맵

int grid[2][3] = {   // 2행 3열
    {1, 2, 3},
    {4, 5, 6},
};
grid[1][2];          // 6 (2번째 행, 3번째 열)

// 메모리엔 1 2 3 4 5 6 처럼 한 줄로 저장(행 우선)

쓰임: 타일 맵·행렬·보드. 크기가 변하면 std::vector<std::vector<int>>나 1차원+인덱스 계산(y*W+x).

C 문자열의 함정

  • char[]는 끝에 널 문자(\0)가 있어야 함
  • ==로 비교하면 주소 비교(내용 아님)
  • 버퍼 크기를 넘겨 쓰면 오버런(보안 취약)
  • 그래서 문자열은 std::string이 기본

멤버하는 일
size()바이트 길이(39)

상황 · 코드 · 쓰임 — string 다루기 + string_view

상황: 문자열을 자르고 합치고 검사. 읽기만 할 땐 복사 없는 string_view.

#include <string>
#include <string_view>

std::string s = "hero_knight";
s.substr(0, 4);            // "hero"
s.find('_');              // 4 (밑줄 위치)
s += "_lv2";             // "hero_knight_lv2"

// 읽기 전용 인자 → 복사 없이 '빌려 보기' (span의 문자열판)
void greet(std::string_view name) {
    // name을 수정하지 않고 읽기만
}
greet(s);      // 복사 안 함
greet("bob");  // 리터럴도 그대로

쓰임: 파싱·로그·이름 처리. string_view는 원본이 살아 있는 동안만 유효(재할당·수명 주의 → 32).

지금은 여기까지: 격자는 2차원 배열, 문자열은 std::string(비교·연결·검색이 안전), 읽기 전용 인자는 string_view. C 문자열의 \0·주소 비교 함정만 기억하면 됩니다.

53 auto · 타입 추론 · decltype

C++

타입을 일일이 적는 대신 컴파일러가 초기값에서 알아내게 하는 auto. 반복자(31)·긴 타입에서 특히 편하지만, const·참조를 떨어뜨리는 함정이 있어 규칙만 알면 됩니다.

auto — 초기값에서 타입 뽑기

auto n = 42;         // int
auto pi = 3.14;      // double
auto s = std::string("hi");  // std::string

std::vector<int> v = {1,2,3};
for (auto it = v.begin(); it != v.end(); ++it) { }  // 긴 반복자 타입 생략
  • 반복자·람다·긴 템플릿 타입에서 코드가 짧아짐
  • 반드시 초기값 필요(그걸로 타입을 정하므로)
  • 타입이 눈에 중요할 땐 그냥 명시하는 게 읽기 좋을 때도

함정 — auto는 const·참조를 벗긴다

auto는 값 복사로 추론합니다. 원본을 참조하거나 const를 유지하려면 직접 붙여야 합니다.

const std::string name = "hero";

auto        a = name;   // std::string (복사! const 떨어짐)
auto&       b = name;   // const std::string&  (원본 참조 — 안전·빠름)
const auto& c = name;   // 같은 뜻, 의도를 명시

// 범위 for에서 특히 중요
for (auto x : big_vec)        { }  // 매 원소 복사(느릴 수 있음)
for (const auto& x : big_vec) { }  // 복사 없음(읽기)

규칙: 읽기만 하면 const auto&, 바꿔야 하면 auto&, 값이 필요하면 auto. 참조 감각 → 11·30

구조적 바인딩과 함께

std::map<std::string,int> m;
for (const auto& [key, val] : m) {
    // key, val 로 바로 꺼내기
}

여러 값을 한 번에 풀어 담기 = 구조적 바인딩(뒤 유틸 심화에서 자세히).

decltype 맛보기

int x = 5;
decltype(x) y = 10;   // x의 타입(int)을 그대로

// 표현식의 타입을 그대로 가져올 때
// (템플릿·제네릭 코드에서 주로)

decltype는 “이 표현식의 타입”을 뽑습니다. 지금은 “그런 게 있다” 정도면 충분.

지금은 여기까지: auto는 초기값에서 타입을 뽑되 복사·const 벗김이 기본. 읽기 순회는 const auto&가 안전판입니다. 이 한 규칙이 auto 함정의 대부분을 막아 줍니다.

54 형변환 4종 (cast)

C++

타입을 바꾸는 명시적 캐스트. C++는 목적별로 넷으로 나눠, “무슨 의도의 변환인지”를 코드에 남기고 위험한 변환은 눈에 띄게 만듭니다. 뭉뚱그린 C 스타일 (int)x보다 안전합니다.

넷을 한눈에

캐스트쓰임안전도
static_cast숫자 변환, 관련 타입 간(정상적인 변환)보통 안전
dynamic_cast다형 계층에서 안전한 down 캐스트(런타임 검사)안전(검사함)

static_cast — 가장 흔함

double d = 3.9;
int n = static_cast<int>(d);   // 3 (버림)

int a = 7, b = 2;
double r = static_cast<double>(a) / b;  // 3.5
// 안 하면 정수 나눗셈으로 3

쓰임: 숫자 타입 변환, enum↔정수, 명확한 상향 변환.

dynamic_cast — 다형 계층

struct Base { virtual ~Base(){} };
struct Dog : Base { void bark(); };

Base* p = get();
if (auto* d = dynamic_cast<Dog*>(p)) {
    d->bark();   // 진짜 Dog일 때만
}   // 아니면 nullptr

쓰임: 부모 포인터가 실제로 어떤 자식인지 안전 확인. 가상 함수(28) 필요.

const_cast — const 떼기

void legacy(char* s);          // const 없는 옛 API

const std::string msg = "hi";
legacy(const_cast<char*>(msg.c_str()));
// 진짜로 값을 수정하면 UB — 읽기 전제일 때만

주의: const를 뗀 뒤 실제 수정은 미정의 동작. const 개념 → 30

reinterpret_cast — 비트 재해석

int x = 0x41424344;
auto* p = reinterpret_cast<unsigned char*>(&x);
// p[0..3] 로 바이트 열 보기 (엔디안 25)

위험: 타입 시스템을 완전히 우회. 직렬화·저수준 외엔 피하세요. 엔디안 → 25

지금은 여기까지: 대부분은 static_cast로 끝. 계층 확인은 dynamic_cast, 나머지 둘은 “정말 필요할 때만”. C 스타일 캐스트는 넷 중 아무거나로 몰래 변해 위험하니 목적을 드러내는 명시적 캐스트를 쓰세요.

55 균일 초기화 {} · nullptr · 리터럴

C++

현대 C++의 초기화 기본은 중괄호 {}. 널 포인터는 nullptr, 그리고 숫자·문자·문자열을 코드에 적는 리터럴 표기까지 — 변수(05)의 실전 마무리.

균일 초기화 {} — 어디서나 같은 문법

int    a{5};
double b{3.14};
std::string s{"hi"};
std::vector<int> v{1, 2, 3};   // 목록도 그대로
Player p{100, 1};              // 구조체/클래스도

int zero{};   // {}만 쓰면 기본값(0)으로 초기화
  • 좁아지는 변환 차단: int x{3.9}; → 컴파일 에러(()는 조용히 3)
  • {}만 쓰면 항상 0/기본값으로 — 쓰레기값 방지
  • 타입·클래스 상관없이 통일된 모양

nullptr — 진짜 널 포인터

int* p = nullptr;   // 아무것도 안 가리킴

if (p == nullptr) { }   // 또는 if (!p)

// 옛 방식의 함정:
// NULL/0 은 '정수 0'이라 함수 오버로딩에서 헷갈림
// nullptr 은 '포인터 전용 널'이라 명확

규칙: 포인터의 “비었음”은 항상 nullptr. 포인터 → 11

좁아지는 변환이 뭐길래

  • int x = 3.9; → 3 (조용히 손실)
  • int x{3.9}; → 에러(손실을 알려 줌)
  • 그래서 {}가 실수를 더 잘 잡음

리터럴 — 값을 코드에 적는 표기

쓰임: 접미사로 타입을 못박고(1.0f), '로 큰 수를 읽기 좋게. 진법 → 05·37

지금은 여기까지: 초기화는 {}(좁아지는 변환·쓰레기값 방지), 널 포인터는 nullptr, 리터럴은 접미사·구분자로 또렷하게. 이 셋이 “요즘 스타일로 값 다루기”의 기본기입니다.

56 RAII — 자원을 객체 수명에 묶기

C++

C++를 관통하는 핵심 관용구. RAII(Resource Acquisition Is Initialization) = “얻는 순간이 곧 객체를 만드는 순간, 놓는 순간이 곧 소멸하는 순간”. 그래서 delete·unlock·close를 깜빡할 수 없게 됩니다.

핵심 — 생성자에서 얻고, 소멸자에서 놓는다

객체가 스코프를 벗어나면 소멸자가 자동으로 불립니다(스택 10). 여기에 “정리”를 넣어 두면, 어떤 경로로 나가도 정리가 보장됩니다.

{
    std::ofstream f("save.txt");   // 생성 = 파일 열기(자원 획득)
    f << "score 1200\n";
    // ...
}   // 여기서 f 소멸 → 파일 자동 닫힘(flush). close() 불필요
  • 해제 코드를 한 곳(소멸자)에만
  • 예외가 나도 스택 풀리며 소멸자가 불려 정리됨
  • return이 여러 개여도 빠짐없이 정리

이미 쓰고 있었다 — 표준의 RAII들

객체획득(생성)해제(소멸)
std::vector (14)메모리 확보메모리 반납
std::unique_ptr (16)객체 소유delete
std::lock_guard (42)lockunlock
std::ofstream (44)파일 열기파일 닫기

이들이 편했던 이유가 전부 RAII입니다. 수동 정리가 필요 없던 것.

왜 좋은가 — raw new와 비교

// ✗ 수동 관리: 예외/조기 return이면 누수
Widget* w = new Widget();
if (fail()) return;   // delete 안 됨 → 누수!
delete w;

// ✓ RAII: 어떤 경로든 자동 정리
auto w = std::make_unique<Widget>();
if (fail()) return;   // w 소멸 → 자동 delete

직접 만들 때

  • 생성자에서 획득, 소멸자에서 해제
  • 복사/이동 정책을 정한다 → 규칙 0/5(29)
  • 대개는 직접 만들 필요 없이 vector·스마트 포인터에 맡기면 끝(규칙 0)
지금은 여기까지: “자원을 객체에 담으면, 그 객체가 사라질 때 자원도 사라진다.” 이 한 문장이 C++ 메모리·파일·락 안전의 8할입니다. 새 자원이 보이면 “이걸 RAII로 감쌀 수 있나?”를 먼저 떠올리세요.

57 생성자 심화 — 초기화 리스트 · explicit · 위임

C++

클래스(12) 생성자의 실전 도구들. 멤버를 제대로 채우는 초기화 리스트, 원치 않는 자동 변환을 막는 explicit, 생성자 중복을 없애는 위임 생성자.

멤버 초기화 리스트 — 대입 말고 초기화

본문에서 =로 넣는 건 “만든 뒤 대입”. 콜론 뒤 초기화 리스트는 “처음부터 그 값으로 초기화” — 더 효율적이고, const·참조 멤버엔 필수입니다.

struct Player {
    int hp;
    const int id;      // const 멤버
    std::string name;

    Player(int id_, std::string n)
        : hp(100), id(id_), name(std::move(n))  // ← 초기화 리스트
    { }
    // id 는 여기서만 초기화 가능(본문 대입 불가)
};
  • const·참조 멤버는 반드시 초기화 리스트로
  • 멤버는 선언 순서로 초기화됨(리스트 순서 아님) — 순서 맞추기
  • 불필요한 기본 생성+대입을 피해 효율적

explicit — 몰래 변환 막기

struct Meters {
    explicit Meters(int m);   // 암시적 변환 금지
};

void move(Meters d);
move(5);            // ✗ int→Meters 자동 변환 차단
move(Meters(5));    // ✓ 명시적으로

쓰임: 인자 하나짜리 생성자에 붙여 “실수로 숫자가 객체로 둔갑”하는 버그 방지.

위임 생성자 — 중복 제거

struct Enemy {
    int hp, atk;
    Enemy(int h, int a) : hp(h), atk(a) {}
    Enemy() : Enemy(100, 10) {}  // 다른 생성자에 위임
};

쓰임: 여러 생성자가 같은 초기화를 공유할 때 한 곳으로 모아 중복을 없앰.

= default · = delete

컴파일러가 만들어 주는 특수 멤버(규칙 0/5(29))를 명시하거나 금지할 수 있습니다.

struct Config {
    Config() = default;                    // 기본 생성자 그대로 생성
    Config(const Config&) = delete;        // 복사 금지
    Config& operator=(const Config&) = delete;
};
// 복사하면 컴파일 에러 — "이건 복사하면 안 돼"를 코드로 강제

쓰임: 유일 소유 자원·싱글턴처럼 복사되면 안 되는 타입에 = delete. 의도를 컴파일러가 지켜 줌.

지금은 여기까지: 멤버는 초기화 리스트로(순서 주의), 한 인자 생성자엔 explicit, 중복 초기화는 위임으로, 금지는 = delete. 생성자를 “의도대로” 다루는 네 가지 손잡이입니다.

58 static 멤버 · friend · 추상 클래스

C++

클래스(12)의 남은 도구 셋. 모든 인스턴스가 공유하는 static 멤버, private에 접근을 허락하는 friend, 그리고 “뼈대만 정하고 구현을 강제”하는 추상 클래스(순수 가상).

static 멤버 — 클래스가 하나만 갖는 것

인스턴스마다가 아니라 클래스 전체가 딱 하나 공유합니다. 생성된 객체 수 세기 등.

struct Enemy {
    static int count;      // 모든 Enemy가 공유(선언)
    Enemy()  { ++count; }
    ~Enemy() { --count; }
};
int Enemy::count = 0;      // 정의(딱 한 번, .cpp에)

Enemy a, b;
Enemy::count;   // 2  (객체 없이 클래스 이름으로 접근)
  • static 멤버 함수는 특정 객체 없이 호출(this 없음)
  • 상수 설정값·팩토리·카운터에

friend — 예외적 접근 허용

class Vec2 {
    int x, y;
    // 이 함수에게만 private 접근 허용
    friend Vec2 operator+(const Vec2&, const Vec2&);
};

Vec2 operator+(const Vec2& a, const Vec2& b) {
    return { a.x + b.x, a.y + b.y };  // private 접근 OK
}

쓰임: 연산자 오버로딩(13)·짝 클래스. 남발하면 캡슐화가 약해지니 최소한으로.

캡슐화 관점

  • friend는 “이 하나만 예외”라는 명시적 허가
  • private을 public으로 여는 것보다 낫지만
  • 가능하면 public 메서드로 해결이 우선

추상 클래스 · 순수 가상 — 인터페이스

가상 함수(28)에 = 0을 붙이면 순수 가상 함수. 하나라도 있으면 추상 클래스가 되어 직접 생성 불가 — 자식이 반드시 구현하게 강제합니다.

struct Shape {                 // 추상 클래스(인터페이스)
    virtual double area() const = 0;   // 순수 가상: 구현 없음
    virtual ~Shape() = default;
};

struct Circle : Shape {
    double r;
    double area() const override { return 3.14159 * r * r; }
};

// Shape s;        // ✗ 추상 클래스는 생성 불가
Shape* p = new Circle{2};   // ✓ 자식으로
p->area();                  // 다형성

쓰임: “이런 기능을 반드시 제공하라”는 계약(인터페이스). 렌더러·전략·플러그인 설계의 기본. 상속·vtable → 28

지금은 여기까지: static=클래스 공유, friend=예외적 접근 허가, 순수 가상(=0)=구현 강제 인터페이스. 셋 다 “아껴서, 의도가 분명할 때” 쓰면 설계가 또렷해집니다.

59 템플릿 특수화 · 가변 인자 템플릿

C++

템플릿(18)의 두 확장. 특정 타입만 다르게 처리하는 특수화, 인자 개수를 자유롭게 받는 가변 인자 템플릿. STL·라이브러리가 안에서 쓰는 기법이라 “읽을 줄” 알면 충분합니다.

템플릿 특수화 — 이 타입만 특별히

일반 템플릿을 두고, 특정 타입일 때만 별도 구현을 제공합니다.

template <typename T>
std::string kind(T)        { return "일반"; }

template <>                          // bool 전용 특수화
std::string kind<bool>(bool)  { return "불리언"; }

kind(42);     // "일반"
kind(true);   // "불리언"

쓰임: 대부분은 일반 처리, 예외적 타입만 다르게(예: std::vector<bool>가 내부적으로 특수화됨). 오버로딩(51)과 사촌.

상황 · 코드 · 쓰임 — 가변 인자 템플릿

상황: 몇 개가 올지 모르는 인자를 하나의 함수로. print(a, b, c, …)처럼.

#include <iostream>

// 폴드 표현식(C++17): 인자들을 하나씩 펼쳐 출력
template <typename... Args>
void print(const Args&... args) {
    ((std::cout << args << ' '), ...);   // 각 인자를 출력으로 펼침
    std::cout << '\n';
}

print(1, "hi", 3.14, 'x');   // 개수·타입 자유

쓰임: 로깅·포맷·std::make_unique처럼 “인자를 그대로 전달”하는 도구. Args...는 타입 묶음(파라미터 팩), args...는 그 값 묶음.

용어 한 줄

  • typename... Args = 타입 여러 개(팩)
  • args... = 값들을 펼침(확장)
  • (f(args), ...) = 폴드 표현식(각 인자에 반복 적용)

언제 직접 쓰나

  • 대부분은 vector·초기화 리스트로 충분
  • 진짜 “임의 개수·임의 타입”을 감쌀 때만
  • 읽고 이해하는 게 먼저, 작성은 필요할 때
지금은 여기까지: 특수화 = 특정 타입만 다르게, 가변 인자 = 개수 자유(Args...+폴드). 직접 짤 일은 드물지만, STL·라이브러리 시그니처에서 자주 만나므로 읽는 눈을 갖추는 게 목표입니다.
